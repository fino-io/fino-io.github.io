# 分页

API 经常通过 List 方法返回集合，但集合大小可能任意增长，影响查询时间和响应大小。因此，返回集合的 RPC **必须**从一开始就提供分页；给已有方法补加分页是向后不兼容的变更。

## 指导

```proto
message ListBooksRequest {
  string parent = 1;
  int32 page_size = 2;
  string page_token = 3;
}

message ListBooksResponse {
  repeated Book books = 1;
  string next_page_token = 2;
}
```

请求必须包含 `page_size` 和 `page_token`，响应必须包含 `next_page_token`。服务可以返回少于 `page_size` 的项目；`page_size` 为零时使用合理默认值，超过最大值时限制为最大值，无效负数应返回 `INVALID_ARGUMENT`。后续请求必须原样复用 `page_token`，且除分页令牌外的参数必须与首次请求匹配。

页令牌是不透明字符串，客户端不得解析、修改或生成。令牌应绑定请求的身份、父集合、过滤条件和排序条件；无效或不匹配的令牌应返回 `INVALID_ARGUMENT`。响应的顺序在翻页期间应稳定，服务应尽量避免重复或遗漏资源。

### 跳过结果

如果 API 支持跳过前 N 个结果，可以提供 `skip`，但这通常比 page token 成本高，且在数据变化时不稳定。只有确有需求时才支持，并记录其性能和一致性语义。

### 令牌不透明

客户端必须把令牌视为不透明值；令牌可以包含游标、签名、过期时间或内部版本信息。服务不得要求客户端理解令牌格式。

### 令牌过期

服务可以使页令牌过期，必须记录期限以及过期后返回的错误。客户端收到令牌过期错误后，应重新执行首个请求，而不是修改旧令牌。

## 向后兼容

分页字段应在 API 首次发布时就存在。新增分页字段到已有响应会改变客户端看到的结果边界，不能视为简单的兼容增强。

## 设计缘由

在数据源无法提供高效游标时，`skip` 可能导致服务退化为扫描前置结果；因此 page token 是默认方案。通过令牌封装服务端游标和请求快照，可以在不暴露内部存储细节的情况下稳定遍历集合。
