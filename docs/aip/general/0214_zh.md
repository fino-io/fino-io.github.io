# 资源过期

客户经常希望提供某个资源或资源属性不再有用或有效的时间（例如轮换的安全密钥）。目前我们建议客户在 `google.protobuf.Timestamp expire_time` 字段中指定确切的“过期时间”；但当用户希望指定相对过期偏移，而不是具体的过期时间时，这会增加用户负担。

此外，人们都理解“生存时间”（time-to-live，通常缩写为 TTL）的概念，但这种字段通常使用以秒为单位的整数表示，在使用自动生成的客户端库时体验并不理想。

## 指导

1. 希望表达过期时间的 API **必须**使用名为 `expire_time` 的 [`google.protobuf.Timestamp`][timestamp] 字段。
2. 希望允许相对过期时间的 API **必须**定义名为 `expiration`（或 `{something}_expiration`）的 `oneof`，其中同时包含 `expire_time` 字段和名为 `ttl` 的独立 [`google.protobuf.Duration`][duration] 字段；后者标记为仅输入。
3. API **必须**始终在 `expire_time` 字段中返回过期时间，获取资源时将 `ttl` 字段留空。
4. 依赖“生存时间”特定语义的 API（例如必须将 TTL 表示为整数的 DNS）**可以**使用 `int64 ttl` 字段，但此时**应**提供 [aip.dev/not-precedent](./0200.md) 注释。

### 示例

```proto
message ExpiringResource {
  // google.api.resource 以及其他注解和字段

  oneof expiration {
    // 此资源被视为过期的 UTC 时间。
    // 输出时总是提供此字段；如果创建时设置了 `ttl`，
    // 则根据 ttl 的值计算该字段。
    google.protobuf.Timestamp expire_time = 2;

    // 仅输入。此资源的 TTL。
    google.protobuf.Duration ttl = 3 [(google.api.field_behavior) = INPUT_ONLY];
  }
}
```

## 设计缘由

### 备选方案

#### 新增名为 `ttl` 的标准字段

我们考虑过允许使用名为 `ttl` 的标准字段来定义过期时间，但这会要求 API 服务持续更新该字段，就像时钟倒计时一样。这可能会给读-改-写生命周期带来问题：资源处理了一段时间后，实际寿命可能因为处理耗时而被延长。

#### 始终使用 `expire_time`

除了少数例外，目前世界基本采用这种方式。在此方案下，我们可以将 `now + ttl = expire_time` 的计算推入客户端库；但这会让命令行和 REST/JSON 使用体验有些令人沮丧。保持现状通常是默认选择，不过许多客户似乎希望能够定义相对过期时间，因为这样更容易，也能避免时区、时钟过期以及其他类似错误。
