# 先例

新指导发布后，已有 API 可能不符合它；有时为了与既有系统保持一致、满足严格性能要求或处理其他实际原因，API 也可能有意偏离标准。审查中同样可能遗漏错误。由于修复历史错误或让标准覆盖所有用例并不总是可行，API 可能长期保留例外，而新 API 又容易复制这些例外。

## 指导

偏离 AIP 时，API 生产者应记录先例及其理由，并评估它是否会被新的 API 或客户端复制。先例不是新 API 的默认许可，也不应只因为某个已有 API 这样做就被照搬。评审应优先寻找符合现行 AIP 的设计；无法遵循时，必须明确写出例外范围、风险和未来迁移路径。

### 局部一致性

如果一个 API 已有大量相同模式，为保持该 API 内部一致性可以延续先例，但这种理由通常只适用于同一 API，不自动适用于其他 API。

### 既有功能

已有公开功能的客户端和用户可能依赖其行为。修复先例时应评估向后兼容性，必要时通过新版本或新资源提供正确设计，而不是静默改变旧语义。

### 遵循外部规范

外部标准、协议或互操作要求可能迫使 API 采用不同命名、类型或错误语义。服务应链接外部规范，说明哪些差异是强制的，并在 API 边界内尽量保持 AIP 的其他原则。

### 遵循既有系统

API 可能必须映射遗留数据库、控制面或供应商协议。不要让底层结构不加思考地泄露到公开 API；应在转换层隔离遗留约束，并记录无法遵循 AIP 的具体原因。

### 及时性

交付压力有时会促成偏离，但“更快发布”通常不足以证明破坏长期一致性。若确实必须先例，应创建后续工作项和负责人，避免临时方案永久化。

### 技术问题

性能、存储、兼容性或工具限制可以构成先例，但必须提供证据、说明替代方案为何不可行，并说明限制解除后如何收敛到标准模式。
