# API 版本管理

本文说明 Google API 使用的版本管理策略，通常适用于 Google 管理的服务。

## 指导

所有 Google API 接口**必须**提供 major 版本号：它编码在 protobuf package 末尾，并作为 REST URI 路径的第一部分。需要不兼容变更时，应根据 [AIP-180](./0180.md) 和 [AIP-181](./0181.md) 按稳定性级别处理。

这里的 major 版本号借用了语义化版本的术语，但 Google API **不得**暴露 minor 或 patch 版本号：使用 `v1`，而不是 `v1.0`、`v1.1` 或 `v1.4.2`。从用户角度看，minor/patch 等价的兼容增强会直接在 major 版本中更新，用户无需迁移即可获得新能力。

### 基于渠道的版本管理

服务可以为 Alpha、Beta、GA 等发布渠道提供不同入口，但每个渠道仍应有明确的 major 版本。弃用功能时必须在文档、响应头或错误中给出迁移信息，并保留足够的过渡期。

#### 弃用 API 功能

弃用应针对具体资源、方法或字段，而不是含糊地弃用整个版本。服务应说明替代方案和计划移除日期；在同一 major 版本中不能直接删除稳定功能。

### 基于发布的版本管理

新 major 版本适用于破坏性变更。旧版本和新版本可以并行运行，且资源名称、类型和跨版本引用的行为必须明确。新 major 版本不应仅为获得新功能而强迫用户迁移。

### 基于可见性的版本管理

实验性或内部 API 可以通过可见性规则限制访问，但可见性不是 major 版本的替代品。一个组件从内部变为公开时，应完成稳定性、兼容性和文档评审。
