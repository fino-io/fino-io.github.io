# 长时运行操作

有些 API 方法需要较长时间才能完成。此时直接阻塞调用通常体验较差，服务应返回一个可供用户稍后查询的承诺。该模式类似 Python 的 [Future][] 或 Node.js 的 [Promise][]：用户得到一个用于跟踪进度并获取结果的令牌。

## 指导

可能耗时较长的 API 方法**应**返回 `google.longrunning.Operation`，而不是最终响应消息：

```proto
rpc CreateBook(CreateBookRequest) returns (google.longrunning.Operation) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books"
    body: "book"
  };
  option (google.longrunning.operation_info) = {
    response_type: "Book"
    metadata_type: "OperationMetadata"
  };
}
```

`response_type` 必须是方法最终返回的消息，`metadata_type` 必须是提供进度信息的消息；二者都必须指定。Operation 的 `name` 是服务范围内唯一的资源名称，客户端可以通过标准 Operations API 查询、等待、取消或删除它。

### 标准方法

Create、Update、Delete 等标准方法使用 LRO 时，仍应遵循各自 AIP 的 HTTP 映射、方法签名和一致性要求。Get 和 List 通常不应使用 LRO，因为它们是读取操作。

### 并行操作

如果客户端同时发起多个 LRO，服务应保证每个 Operation 独立跟踪，客户端不得依赖完成顺序。资源之间存在依赖时，客户端应等待前置 Operation 完成后再发起后续操作。

### 过期

服务可以在一段时间后删除已完成的 Operation，但必须在文档中说明保留期限；客户端不应长期依赖已完成 Operation 的存在，而应在需要时持久化最终结果。

### 错误

失败时应在 Operation 的 `error` 字段返回 `google.rpc.Status`，并使用 AIP-193 的规范错误码；Operation 完成后不得同时设置 response 和 error。

### 向后兼容

把同步方法改成返回 LRO 会改变 API 的响应类型和客户端调用模型，因此是破坏性变更。API 应在首次设计时决定是否需要长时运行，并在稳定版本中保持该选择。

## 设计缘由

`validate_only` 请求不得创建持久 Operation，除非 API 明确需要返回完整的异步验证结果；如果验证本身耗时较长，可以返回一个只执行验证的 Operation。将进度和最终结果分离，能让客户端在不保持长连接的情况下可靠地恢复工作。
