# 向后兼容

API 是与用户签订的契约。除非稳定性级别另有说明，服务发布新的 minor 或 patch 版本时，**不得**破坏已有客户端；相同 major 版本的新服务器必须能与旧客户端工作。本页是判断标准的指导性清单，而非穷尽列表。

## 指导

通常兼容的变更包括增加可选字段、增加响应字段、增加 enum 值、增加新的方法和服务，以及增加不改变既有语义的 URI 绑定。通常不兼容的变更包括删除或重命名字段、方法、服务或 enum 值，改变字段类型或资源名称，修改必填性，改变既有字段的含义、默认值或序列化格式。

### 增加组件

增加请求中的可选字段通常兼容；增加响应字段也通常兼容，但不能改变旧字段的含义。增加 enum 值时，客户端必须能处理未知值。新增方法和服务不会影响不使用它们的客户端，但可能需要更新生成客户端。

### 删除或重命名组件

删除或重命名公开字段、消息、服务、方法、enum 值和 URI 绑定通常是破坏性变更。应先弃用并保留兼容别名，再在新的 major 版本中删除。

### 移动文件与 oneof

在文件之间移动定义、改变包路径或把已有字段移入/移出 `oneof` 可能改变生成代码和 wire 行为，因此应视为不兼容。向已有 oneof 增加字段通常兼容。

### 改变字段类型和字符串长度

改变字段类型、编码、精度或允许的值范围可能破坏客户端。即使语言类型看似兼容，也要检查 protobuf wire、JSON、验证器和生成代码。放宽字符串最大长度通常有风险，因为客户端可能依赖长度限制；缩短或改变格式更明显不兼容。

### 改变资源名称

资源名称模式、集合键、父资源关系和资源类型标识符属于公开契约，不能在同一 major 版本中改变。需要迁移时应发布新资源或新 major 版本，并提供转换方案。

### 语义变更

改变成功/失败条件、权限、排序、分页、过滤、幂等性、错误码或副作用都是潜在破坏性变更。尤其不得改变默认值的语义、缺省字段的序列化方式，或让同一字符串在新版本中表示不同值。

#### 值格式与构造

若客户端会持久化、比较或拼接字段值，改变值的格式、大小写、生成规则或规范化方式就可能破坏客户端。新增值应保持旧值仍然有效。

#### 默认值不得改变

服务端默认值属于契约。改变默认排序、分页大小、字段行为、超时或策略可能让旧客户端得到不同结果，必须在兼容性评审中单独说明。

#### 默认值的序列化

客户端可能依赖 JSON 或 protobuf 中默认值的出现/省略方式。新增或移除默认值的序列化可能破坏签名、缓存和差异比较，不应轻易改变。

## 设计缘由

字符串长度、格式和默认值变化的风险常被低估，因为源码层面看起来只是“放宽限制”。实际上客户端可能用这些约束做校验、分片、缓存键或权限判断，任何语义改变都应按契约变更处理。
