# 授权校验

大多数操作，无论是读取还是写入，都需要授权，即执行用户请求操作的权限。此外，还必须谨慎控制向*未授权*用户提供的信息量，因为信息泄漏可能造成安全问题。

## 指导

服务**必须**在校验任何请求之前先检查授权，以确保 API 表面安全并提供一致的用户体验。一个操作**可以**需要多个权限或前置条件才能获得授权。

如果请求因任何原因无法通过授权校验，服务**必须**返回 `PERMISSION_DENIED` 错误，对应的错误消息**应**类似于：“Permission '`{p}`' denied on resource '`{r}`' (or it might not exist).”这可以避免泄露资源是否存在。

如果由于资源不存在而无法确定授权，服务**应**检查读取父资源子资源的授权；如果授权校验通过，则返回 `NOT_FOUND`。

### 多个操作

服务可能遇到这样的情况：它有两个权限不同的操作，调用其中任一操作都能暴露资源存在，但用户只有权限调用其中一个。

在这种情况下，服务**仍应**只检查与当前调用操作有关的授权，**不应**通过检查其他相关授权来“帮忙”，因为这类算法很难正确实现，容易意外泄漏信息。

例如，假设：

- 某个集合中存在一个资源，但用户无权读取该集合。
- 用户确实可以创建其他资源，且集合使用用户指定 ID（这意味着重复 ID 导致的失败会暴露资源存在）。

在这种情况下，Get 或 Create 方法在决定返回哪种错误时，**仍应**只检查*自己的*权限，而不检查对方的权限。

## 设计缘由

[RFC 7231 §6.5.3][] 规定，在服务不希望泄露资源存在的情况下，可以使用 `404 Not Found` 代替 `403 Forbidden`；而本 AIP 主张使用 `PERMISSION_DENIED`（在 HTTP 中对应 `403 Forbidden`）。我们基于以下原因采取这一立场：

- “先返回 `404 Not Found`，直到拥有足够权限后再返回 `403 Forbidden`”的做法反直觉，并增加了排查问题的难度。
  - 服务**可以**在继续使用 `404 Not Found` 状态码的同时提供缺少的权限信息，以缓解这一问题，但这会传达混合信息。
- `403 Forbidden` 基本上总是需要人工处理的错误，而 `404 Not Found` 经常是应用可以处理的有效响应（例如“获取或创建”）；将其用于权限错误会让应用失去这一优势。
- RFC 7231 §6.5.4 规定 `404 Not Found` 结果可缓存，但权限错误通常不可缓存。按条件发送显式缓存控制可以缓解这一问题，但会违背初衷。
- 本文指导与大多数现实中的其他授权系统更加一致。

[rfc 7231 §6.5.3]: https://tools.ietf.org/html/rfc7231#section-6.5.3
