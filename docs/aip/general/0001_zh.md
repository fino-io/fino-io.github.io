# AIP 的目的与指南

随着 Google API 数量不断增长，API 治理团队也不断扩充，以满足 API 维护需求。API 生产者、评审者和其他相关人员越来越需要一套可参考的 API 文档。API 风格指南和 One Platform 入门文档有意保持简短且高度概括，而 AIP 集合为 API 设计指导提供了一种一致的文档方式。

## 什么是 AIP？

AIP 是 **API Improvement Proposal**（API 改进提案）的缩写，是一类为 API 开发提供高层次、简明说明的设计文档。AIP 是 Google API 相关文档的事实来源，也是 API 团队讨论 API 指导并达成共识的方式。AIP 以 Markdown 文件的形式维护在 [AIP GitHub 仓库](https://github.com/aip-dev/google.aip.dev)中。

## AIP 的类型

AIP 目前有以下类型，类型列表会根据需要演进。

### 指导

这类 AIP 描述 API 设计指导，为 API 生产者编写简单、直观且一致的 API 提供建议，也为 API 评审者提供评审依据。

### 流程

这类 AIP 描述 API 设计相关流程。它们通常会影响 AIP 流程本身，用于改进 AIP 的处理方式。

## 参与者

评审和处理 AIP 涉及多个参与者。下面是从 API 生产者开始的升级路径：

```text
API 生产者 → AIP 编辑
                  ├→ 基础设施技术负责人 → 技术负责人
                  └→ 设计技术负责人 → 技术负责人
```

如上图所示，技术负责人是 AIP 流程的最终决策者，也是必要时的最终升级对象。

### 编辑

编辑是负责对 AIP 作出决策的一组人员。AIP 流程的总体目标是协作，并尽可能基于共识工作。但流程仍需要数量有限的指定批准者；这些 Google 员工负责通用 Scope 中每份 AIP 的批准。

编辑还负责推动 AIP 的行政和编辑工作，并管理 AIP 的流水线与工作流。他们批准 AIP 的 PR、分配提案编号、管理议程、设置 AIP 状态等，也确保 AIP 具备良好的可读性（拼写、语法、句子结构、标记格式等）。

AIP 编辑资格由现任编辑邀请产生。

## 特定领域的 AIP

某些 AIP 可能只适用于特定领域，例如某个产品领域甚至某个团队内的 API。此时，该群体会根据 AIP-2 获得一个专用 AIP 编号区间，相关 AIP 也会明确标注自己的 Scope。

## 状态

AIP 在流程中可能处于多种状态：

### Draft（草案）

Draft 是 AIP 的初始状态，表示 AIP 主要由原始作者讨论和迭代。编辑可以在此阶段介入，但不是必须的。

> **注意：** 如果需要进行重要的高层次迭代，建议先在 Google 文档中起草，而不是直接创建 PR。从 Google 文档迁移到 AIP 系统的文档，如果获得了充分批准，可以跳过 Draft，直接进入 Reviewing。

### Reviewing（评审中）

当 AIP 的讨论基本结束、但尚未正式接受时，它会进入 Reviewing。此时作者已对提案达成总体共识，编辑开始介入；编辑可以要求修改或提出替代方案。

> **注意：** 从正式流程看，除作者外至少一名 AIP 批准者必须正式签字，AIP 才能进入 Reviewing；其他批准者也不得在 GitHub PR 中提出正式反对意见（“要求修改”）。

### Approved（已批准）

AIP 获得批准后进入 Approved 状态，并被视为“当前最佳实践”。除作者外，至少两名 AIP 批准者必须正式签字，且其他批准者不得在 PR 中提出正式反对意见。

### Withdrawn（已撤回）

如果作者或发起人撤回 AIP，它会进入 Withdrawn 状态。撤回的 AIP 可以由另一位发起人重新接手。

### Rejected（已拒绝）

如果 AIP 被编辑拒绝，它会进入 Rejected 状态。被拒绝的 AIP 会保留，用于记录背景并为未来讨论提供参考。

### Deferred（已延期）

如果一份 AIP 在较长时间内没有进展，编辑可以将其标记为 Deferred。

### Replaced（已替代）

如果一份 AIP 被另一份 AIP 替代，它会进入 Replaced 状态。编辑负责说明替代关系及其理由，新的 AIP 也应清楚说明这一理由。

通常，API 生产者应优先依赖 Approved 状态的 AIP。

## 工作流

下面的工作流描述如何提出 AIP，以及如何将 AIP 从提案推进到实现和最终批准。

### 概览

```text
Draft → Reviewing → Approved → Replaced
  └──────────────→ Withdrawn / Rejected / Deferred
Reviewing ───────→ Withdrawn / Rejected / Deferred
```

### 提出 AIP

提出 AIP 前，先 [创建 issue](https://github.com/aip-dev/google.aip.dev/issues)，让大家对基本想法提供初步反馈。通常，想法应能在几页内说明清楚。

提出新 AIP 或修改现有 AIP 时，最好引用会受到提案影响的先例或示例用例，使提案建立在真实的问题空间上。因此，提案**应**提供具体引用或定义清晰的示例，例如外部 RFC 或标准、采用相似模式的一组 API，以及尚未解决的具体用例。

准备就绪后，在 AIP 目录中创建一个新文件，并以 `aip/new.md` 为文件名创建 PR，确保维护者可以编辑该 PR。

通常，编辑会为提案分配 AIP 编号，并以 Reviewing 状态提交 PR。如果提案已在其他 AIP 中讨论并被拒绝，或提案本身明显不可行，编辑也可能直接拒绝，不予合并。

### 讨论 AIP

PR 合并后，AIP 作者负责在后续的批准 PR 中推动 AIP。这意味着作者需要推动提案达成共识，必要时参加 API 治理团队的定期会议。讨论期间，作者可以通过向 PR 提交后续 commit 修改 AIP。

### 接受 AIP

编辑会共同确保合格的提案不会长期停留在评审中。

要获得最终批准，一份 AIP 至少必须获得负责该领域的技术负责人（设计或基础设施）以及另一名编辑的批准，并且没有编辑主动要求修改。如果 AIP 编辑本人是主要作者，则至少还需要两名其他编辑批准。

AIP 获得批准后，编辑会更新状态并提交 PR。

### 撤回或拒绝 AIP

作者经过进一步考虑后，可以决定不再推进 AIP，并在 PR 中添加带理由的撤回说明。编辑也可能在团队无法达成共识时拒绝 AIP，并在 PR 中添加带理由的拒绝说明。随后编辑更新状态并提交 PR。

### 替代 AIP

在少数情况下，一份 AIP 可能需要被另一份 AIP 替代。这不是常规做法：已批准 AIP 的小幅编辑是允许的，也是调整指导的常见方式。但如果新指导从根本上改变了旧指导，编辑应创建一份新的 AIP；新 AIP 批准后替代旧 AIP，旧 AIP 进入 Replaced 状态并链接到新的当前 AIP。
