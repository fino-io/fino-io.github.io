# 字段

[`google.api.FieldInfo`][field info proto] 类型通过配套的 `google.api.field_info` 扩展，能够在基本的名称和类型信息之外进一步丰富字段模式。

## 指导

只有在本 AIP 或其他使用 `google.api.FieldInfo` 信息的 AIP 明确要求时，才需要为字段添加 `google.api.field_info`。因此，本文的指导同样适用于这些场景。

### 格式

原始类型的字段仍然可以具有特定格式。要表达这种类型格式，应通过 `(google.api.field_info).format` 扩展字段使用 `FieldInfo.Format` 枚举。以下指导说明每个 `FieldInfo.Format` 值的含义及使用要求。

#### UUID4

`UUID4` 格式表示由 [RFC 4122][] 规定的 UUID 版本 4 值。它**只能**用于 `string` 类型字段。

服务**可以**将这类值规范化为全部小写字母。例如，`F47AC10B-58CC-0372-8567-0E02B2C3D479` 会被规范化为 `f47ac10b-58cc-0372-8567-0e02b2c3d479`。

因此，**不得**通过原始文本比较进行等价性比较，而**必须**使用符合 [RFC 4122][] 的实现。

#### IPv4

`IPV4` 格式表示由 [RFC 791][] 规定的 IPv4 地址。它**只能**用于 `string` 类型字段。

服务**可以**压缩此类值，去掉每个八位组中的前导零。例如，`001.022.233.040` 会被压缩为 `1.22.233.40`。

因此，**不得**通过原始文本比较进行等价性比较，而**必须**使用符合 [RFC 791][] 的实现。

#### IPv6

`IPV6` 格式表示由 [RFC 4291][] 规定的 IPv6 地址。它**只能**用于 `string` 类型字段。

服务**可以**按照 [RFC 5952][]，将此类值规范化为全部小写并压缩零。例如，`2001:0DB8:0::0` 会被规范化为 `2001:db8::`。

因此，**不得**通过原始文本比较进行等价性比较，而**必须**使用符合 [RFC 4291][] 的实现。

#### IPv4 或 IPv6

`IPV4_OR_IPV6` 表示字段可以是 IPv4 或 IPv6 地址，具体见 [IPv4](#ipv4) 和 [IPv6](#ipv6) 章节。

#### 格式兼容性

为已有的、未指定格式的字段增加格式说明*不具有*向后兼容性，除非该字段一直都符合要指定的格式。

在任何情况下，将已有格式说明改为另一种格式都*不具有*向后兼容性。

#### 扩展格式

任何新的 `FieldInfo.Format` 值**必须**受[IETF 批准的 RFC][ietf rfc]或 [Google 批准的 AIP](./0001.md) 约束。

## 设计缘由

#### 为什么增加格式说明？

原始类型字段的格式可能对其可用性至关重要。有些编程语言会将特定的类型格式作为独立类型表达，例如 Java 的 [UUID][java uuid]。大多数格式都有由服务验证的具体结构要求，因此提前向用户传达格式对用户体验很重要。

#### 为什么不鼓励原始类型的等价比较？

受支持格式的文本表示存在许多细节差异，将值转换为规范表示并不简单。因此，要让每个消费者和每个服务之间的实现完全一致，实际上不可行。

#### 为什么要记录值的规范化？

虽然不建议对任何受支持格式使用原始比较，但统一规范化值对于建立消费者预期、创建易用的 API 表面很重要。

#### 为什么要求新格式必须有 RFC 或 AIP？

足够标准化、值得制定 RFC 或 AIP 的格式，足够稳定且广为人知，可以作为受支持的值纳入 Google API。要求额外的指导意味着格式规范的治理不由 `FieldInfo.Format` 枚举本身负责。
