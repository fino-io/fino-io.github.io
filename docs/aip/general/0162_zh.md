# 资源修订版本

有些 API 需要保存资源的历史状态，让用户能够回滚或与历史状态比较，或把某一时刻的资源快照作为其他数据的依据。本文使用“修订版本”表示资源的历史引用，避免与 API 整体的“版本”混淆。

**注意：** 本 AIP 当前为 Draft，正文稳定性低于 Approved AIP。

## 指导

API **可以**为具有修订历史的资源定义嵌套 `revisions` 集合。修订版本应是不可变资源，包含其对应资源的快照、创建时间和必要的父资源引用；修订版本的名称应稳定且可长期引用。

### 创建修订版本

服务可以在每次资源变更时自动创建修订版本，也可以通过显式方法创建。必须记录修订版本对应的资源状态点，并明确是否每次更新都会产生修订版本。

### 修订版本名称

修订版本名称**应**类似 `{resource}/revisions/{revision}`，且修订版本 ID 在资源范围内唯一。修订版本不得复用普通资源名称空间，以免把历史对象误当成当前资源。

### 服务端别名

服务可以提供指向特定修订版本的只读别名（如 `latest` 或 `current`），但别名不是不可变版本，不能作为审计或回滚的永久依据。

### 用户指定别名

如果用户需要给修订版本打标签，可以定义别名资源。别名必须明确同一时刻是否只能指向一个修订版本，更新别名不应修改历史修订版本本身。

### 回滚

回滚应通过 Update 或专用自定义方法完成，并创建新的当前修订版本；不能直接把当前资源的版本指针改回旧版本而不留下历史记录。回滚操作应支持 ETag/并发校验，并遵循权限和强一致性要求。

### 子资源

修订版本中的子资源快照应明确是深拷贝、引用还是独立修订。若子资源本身有修订历史，服务应记录父修订版本与子修订版本的对应关系。

### 标准方法

修订版本通常支持 Get 和 List；Create、Update、Delete 是否支持取决于模型。不可变修订版本不应通过 Update 修改，删除历史版本必须有明确的保留和审计语义。

## 设计缘由

将修订版本抽象为嵌套集合，既保留资源名称层次，也允许标准 List 分页和权限控制。使用别名可以提供易读入口，但将别名与不可变修订版本分开，能避免别名移动破坏历史引用。

## 历史

本文曾考虑把修订版本作为集合扩展，后改为子集合，以更好地遵循资源名称和标准方法模型；也从使用 tag 标识切换为使用资源 ID，以避免别名和实体身份混淆。
