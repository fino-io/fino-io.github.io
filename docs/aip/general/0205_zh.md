# 阻断 Beta 发布的变更

API 通常会先发布 Alpha 版本，以便获得客户的早期反馈。此时 API 仍是临时性的，在吸收重要反馈并稳定为 Beta 之前可能会多次变更。

由于 Alpha 的目的是收集反馈，API 不需要一开始就完美，API 作者也不必严格解决所有易用性问题或 API 标准中的每个细节。API 作者和评审者经常不会对最佳设计达成一致，而让用户实际试用 API 往往是找出答案的最佳方式。

然而，收集反馈并准备将 API 晋级 Beta 后，就需要解决易用性和风格问题。为确保这些问题不会被遗忘，应在 API 中明确记录它们。

## 指导

如果 API 存在易用性问题或违反 API 标准，且当前设计在带入 Beta 版本之前需要额外审查，则**必须**在内部注释中使用其描述性链接（[aip.dev/beta-blocker]()）链接到本文，以确保 API 发布 Beta 前完成修正。

注释**还必须**说明 Beta 阶段应进行何种变更。例如：

```proto
message InputConfig {
  // 输入参数。
  // (-- aip.dev/beta-blocker: 在 Beta 发布前，将已知参数转换为显式字段。 --)
  map<string, string> parameters = 1;
}
```

如果 API 标准例外确实需要延续到 Beta 和 GA，请参阅 [AIP-200][]。
