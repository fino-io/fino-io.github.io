# 资源名称

大多数 API 都会暴露资源（其主要名词），供用户创建、获取和操作。此外，资源还具有*名称*：每个资源都有一个唯一标识符，用户用它来引用该资源；这些名称就是用户应当*存储*为资源规范名称的值。

## 指导

API 定义的所有资源名称在该 API 内**必须**唯一。（关于跨 API 引用资源的更多信息，请参阅下文的[完整资源名称](#完整资源名称)章节。）

资源名称按照 [URI 路径模式][uri path schema]格式编排，但不包含开头的斜杠：

    publishers/123/books/les-miserables
    users/vhugo1802

- 资源名称的组成部分**通常应**在集合标识符（例如 `publishers`、`books`、`users`）和资源 ID（例如 `123`、`les-miserables`、`vhugo1802`）之间交替出现。
- 资源名称**必须**使用 `/` 字符分隔各个片段。
  - 资源名称的非末尾片段**不得**包含 `/` 字符。
  - 资源名称的末尾片段**不应**包含 `/` 字符。
- 资源名称**应**只使用 DNS 名称中可用的字符，具体定义见 [RFC-1123](https://tools.ietf.org/html/rfc1123)。
  - 此外，资源 ID **不应**使用大写字母。
  - 如果确实需要额外字符，资源名称**不应**使用需要 URL 转义的字符或 ASCII 之外的字符。
  - 如果无法避免 Unicode 字符，资源名称**必须**以规范化形式 C 存储（参见 [AIP-210][]）。
- 资源**必须**暴露包含其资源名称的 `name` 字段。
  - 资源**可以**单独提供资源 ID（例如 `book_id`）。该字段**必须**应用 [`OUTPUT_ONLY`](./0203.md#output-only) 字段行为分类。
  - 资源**可以**暴露单独的、由系统生成的唯一 ID 字段[（`uid`）](./0148.md#uid)。该字段**必须**应用 [`OUTPUT_ONLY`](./0203.md#output-only) 字段行为分类。
  - 资源**不得**暴露元组、自链接或其他形式的资源标识。
  - 所有 ID 字段**应**使用字符串类型。

**注意：** 此处所述的资源名称在单个 API 范围内使用（或者在拥有该资源的 API 可以从上下文中明确确定的情况下使用），只需要在该范围内唯一。因此，为了与下文讨论的*完整资源名称*区分，它们有时也被称为*相对资源名称*。

[aip-210]: ./0210.md
[uri path schema]: https://datatracker.ietf.org/doc/html/rfc3986#appendix-A

### 集合标识符

资源名称中的集合标识符片段**必须**是资源所用名词的复数形式。（例如，`Publisher` 资源的集合在资源名称中称为 `publishers`。）

- 集合标识符**必须**是简洁的美式英语术语。
- 集合标识符**必须**使用 `camelCase`。
- 集合标识符**必须**以小写字母开头，且只包含 ASCII 字母和数字（`/[a-z][a-zA-Z0-9]*/`）。
- 集合标识符**必须**使用复数形式。
  - 如果没有复数词（如 “info”），或者单数和复数形式相同（如 “moose”），则使用不变的（单数）形式才是正确的。这种情况下，集合片段**不得**通过添加 “s” 来生造单词（例如避免使用 “infos”）。
- 在任意一个资源名称中，集合标识符**必须**唯一。（例如 `people/xyz/people/abc` 无效。）

#### 嵌套集合

如果资源名称包含多个层级，且父集合的名称被用作子资源名称的前缀，则子集合名称**可以**省略该前缀。例如，对于通常嵌套在 `users` 之下的 `UserEvent` 资源集合：

```
users/vhugo1802/userEvents/birthday-dinner-226
```

API **应**使用冗余更少的形式：

```
users/vhugo1802/events/birthday-dinner-226
```

在这种情况下，*消息*和*资源类型*仍然称为 `UserEvent`；只有模式中的集合标识符和资源标识符被缩短。由于*资源类型*没有缩短，`singular` 和 `plural` 同样**不应**缩短。

```
message UserEvent {
  option (google.api.resource) = {
    type: "example.googleapis.com/UserEvent"
    // 只有 `pattern` 中的集合和资源标识符被缩短。
    pattern: "projects/{project}/users/{user}/events/{event}"
    singular: "userEvent"
    plural: "userEvents"
  };

  string name = 1;
}
```

**注意：** API 如果希望采用这种方式，就**必须**在其定义的所有 `pattern` 条目中，以及 API 引用该资源的其他位置，始终一致地遵循此格式；否则就完全不要采用这种方式。

### 资源 ID 片段

资源 ID 片段用于标识其父集合中的资源。在资源名称 `publishers/123/books/les-miserables` 中，`123` 是出版商的资源 ID，`les-miserables` 是图书的资源 ID。

- 如果资源 ID 由用户指定，API **必须**记录允许的格式。用户指定的资源 ID **应**遵循 [RFC-1034][]，即只包含字母、数字和连字符，首字符为字母，末字符为字母或数字，最多 63 个字符。
  - 此外，用户指定的资源 ID **应**限制字母为小写（`^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$`）。
  - **不应**允许 ASCII 之外的字符；但如果确实需要 Unicode 字符，API **必须**遵循 [AIP-210][] 的指导。
- 如果资源 ID 不能由用户设置，API **应**记录其基本格式以及上限（例如“最多 63 个字符”）。
- 更多信息请参阅 [Create][] 标准方法。

[Create]: ./0133.md#user-specified-ids
[RFC-1034]: https://tools.ietf.org/html/rfc1034

### 资源 ID 别名

为资源 ID 的常见查询模式提供别名有时很有价值。例如，资源层级顶部有 `users` 的 API，可能希望提供 `users/me` 作为获取当前已认证用户信息的快捷方式。

API **可以**为常见查询模式提供程序化别名。不过，API 返回的所有数据**必须**使用规范资源名称。

### 完整资源名称

大多数情况下，资源名称只在单个 API 中使用，或者在拥有资源的 API 可以从上下文中明确确定的场景中使用（例如 `string pubsub_topic`）。

然而，有时服务需要引用任意 API 中的资源。这种情况下，服务**应**使用*完整资源名称*：一种无模式 URI，依次包含拥有资源的 [API 服务名称](./0009.md#api-service-name) 和相对资源名称：

```
//library.googleapis.com/publishers/123/books/les-miserables
//calendar.googleapis.com/users/vhugo1802
```

**注意：** 对于拥有 API 已经明确的跨 API 引用，**不应**使用完整资源名称；只有字段可能引用多个 API 中的资源、存在歧义时才使用它。

### 资源 URI

完整资源名称是一种无模式 URI，但与我们用于访问资源的完整 URI 略有不同。后者包含协议（HTTPS）、API 版本和要访问的特定[服务端点](./0009.md#api-service-endpoint)：

```
https://library.googleapis.com/v1/publishers/123/books/les-miserables
https://calendar.googleapis.com/v3/users/vhugo1802
```

完整资源名称中不包含版本，因为完整资源名称预期会跨版本持久存在。即使 API 表面在不同主版本间发生变化，同一 API 的多个主版本也应使用相同的底层数据。

**注意：** 完整资源名称与服务端点之间的对应关系依赖约定。特别是，一个服务可以拥有多个端点（例如区域化、mTLS 和私有访问），完整资源名称不会因此改变。

### 表示资源名称的字段

定义资源时，第一个字段**应**是资源名称，类型**必须**为 `string`，且资源名称字段**必须**称为 `name`。消息**应**包含声明类型的 `google.api.resource` 注解（关于此注解的更多信息，请参阅 [AIP-123][]）。

```proto
// 图书馆中一本图书的表示。
message Book {
  option (google.api.resource) = {
    type: "library.googleapis.com/Book"
    pattern: "publishers/{publisher}/books/{book}"
  };

  // 图书的资源名称。
  // 格式：publishers/{publisher}/books/{book}
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];

  // 其他字段……
}
```

定义获取或操作已存在资源的方法（例如 `GetBook` 或 `ArchiveBook`）时，请求消息的第一个字段**应**是资源名称，类型**必须**为 `string`，且资源名称字段**必须**称为 `name`。该字段**还应**使用 `google.api.resource_reference` 注解，并引用资源类型（[AIP-123][]）。

```proto
// ArchiveBook 的请求消息。
message ArchiveBookRequest {
  // 要归档的图书。
  // 格式：publishers/{publisher}/books/{book}
  string name = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      type: "library.googleapis.com/Book"
    }];

  // 其他字段……
}
```

**注意：** 除此用途外，字段**不得**称为 `name`。对于其他使用场景，应使用不同术语，或添加形容词前缀（例如 `display_name`）。

[AIP-123]: ./0123.md

### 表示资源父级的字段

定义从集合中获取资源或向集合中添加新资源的方法（例如 `ListBooks` 或 `CreateBook`）时，请求消息的第一个字段**应**为 `string` 类型，并且对于集合的资源名称，**应**称为 `parent`。`parent` 字段**还应**使用 `google.api.resource_reference` 注解，并引用父资源类型（[AIP-123][]）。

```proto
// ListBooks 的请求消息。
message ListBooksRequest {
  // 要列出其图书的出版商。
  // 格式：publishers/{publisher_id}
  string parent = 1 [(google.api.resource_reference) = {
    type: "library.googleapis.com/Publisher"
  }];

  // 其他字段（例如 page_size、page_token、filter 等）……
}
```

如果可能的父类型不止一种，`parent` 字段**应**改为在 `google.api.resource_reference` 上使用 `child_type` 键进行标注：

```proto
// ListBooks 的请求消息。
message ListBooksRequest {
  // 要列出其图书的父资源。
  // 格式：
  //   - publishers/{publisher_id}
  //   - authors/{author_id}
  string parent = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      child_type: "library.googleapis.com/Book"
    }];

  // 其他字段（例如 page_size、page_token、filter 等）……
}
```

**注意：** 除此用途外，字段**不应**称为 `parent`。对于其他使用场景，应尽可能使用同义词。

### 表示其他资源的字段

如果字段表示另一个资源，字段**应**为 `string` 类型，并接受另一个资源的资源名称。字段名**应**等价于对应消息名称的 snake case 形式。

- 字段名**可以**在适当时包含形容词前缀（例如 `string dusty_book`）。
- 除非没有该后缀字段就会产生歧义（例如 `crypto_key_name`），否则字段名**不应**使用 `_name` 后缀。
- 表示其他资源的字段**应**提供 `google.api.resource_reference` 注解，并标明被引用的资源类型。
- 如果无法使用资源名称，而必须严格使用 ID 片段，字段**应**使用 `_id` 后缀（例如 `shelf_id`）。

字段**不应**使用实现该资源的 `message` 作为 `message` 类型，以下情况除外：

- API 仅供内部使用，资源之间具有紧密的生命周期关系，且权限模型支持对嵌入资源继承访问权限。
- 按照 AIP-162 修订模式嵌入资源。

资源引用示例：

```proto
// 图书馆中一本图书的表示。
message Book {
  option (google.api.resource) = {
    type: "library.googleapis.com/Book"
    pattern: "publishers/{publisher}/books/{book}"
  };

  // 图书名称。
  // 格式为 `publishers/{publisher}/books/{book}`。
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];

  // 图书当前所在的书架。
  // 格式为 `shelves/{shelf}`。
  string shelf = 2 [(google.api.resource_reference) = {
    type: "library.googleapis.com/Shelf"
  }];

  // 其他字段……
}
```

## 设计缘由

### 使用名称而不是 ID

对于任何大型系统，都存在许多种资源。若要使用简单的资源 ID 标识资源，实际上需要使用特定于资源的元组才能可靠地定位资源，例如 `(bucket, object)` 或 `(user, album, photo)`。这会带来几个问题：

* 开发者必须理解并记住这些没有语义的元组。
* 传递元组通常比传递字符串更困难。
* 日志、访问控制等集中式基础设施无法理解专用元组。
* 专用元组限制了 API 设计的灵活性，例如无法提供可复用的 API 接口。比如，[长时运行操作][aip-151] 可以与许多其他 API 接口协同工作，正是因为它们使用灵活的资源名称。

[aip-151]: ./0151.md

### 统一使用 `name`

资源名称这一概念并不新鲜，它与统一资源标识符（URI）和统一资源定位符（URL）一起，在统一资源名称（URN）中得到形式化。考虑到 “name” 这个术语在一般语境中含义过于广泛，如果不明确限定含义，会让开发者感到困惑。因此，在符合 AIP 的 API 中保留 `name` 作为字段名，可以消除与资源名称混淆的可能，并迫使其他原本会使用 “name” 的字段采用更具体的字段名称。

### 禁止嵌入资源

直接将资源消息用作另一个资源中字段的类型会产生以下问题：

* 使资源生命周期复杂化：如果依赖资源被删除，依赖资源中嵌入的引用会怎样？数据保留和清理操作会显著复杂化。
* 绕过权限：如果每个资源都有自己的权限，拥有依赖资源读取权限、却没有依赖资源本身相同权限的用户，突然就无法看到完整资源。
* 在所有方面紧密耦合资源：改变任一资源在模式、权限或其他方面的要求都会影响另一个资源，显著增加发布的复杂度。

按照建议使用名称引用，可以避免复制资源数据，强制所属服务参与引用解析（通过标准方法），从而消除全部这些复杂度，并保证每个资源的逻辑关注点彼此隔离。

## 历史

### 禁止用户指定的 ID 使用 UUID

作为让 API 更加声明式友好的一项工作，API 被要求允许用户在创建时指定资源 ID。与此同时，还鼓励增加一个包含 UUID 的支持字段 `string uid`。随后增加指导，劝阻将*用户指定的资源 ID*设置为 UUID，甚至设置为看起来像 UUID 的值。

表面上看，`uid` 包含服务生成的 UUID 这一事实促成了对用户指定资源 ID 的限制，目的是迫使用户指定的资源 ID 更有“意义”。然而，我们后来不再认为此要求有价值，因此将其移除。
