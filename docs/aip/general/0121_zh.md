# 面向资源的设计

面向资源的设计是一种用于定义 [RPC][] API 的模式，建立在若干高层设计原则之上（其中大多数原则也常见于近期的公开 HTTP API）：

- API 的基本构件是具有独立名称的*资源*（名词），以及资源之间存在的关系和层级结构。
- 少量标准*方法*（动词）为大多数常见操作提供语义。不过，当标准方法不适用时，可以使用自定义方法。
- 无状态协议：客户端与服务器之间的每次交互彼此独立，且客户端和服务器各自承担清晰的职责。

读者可能会注意到这些原则与 [REST][] 的某些原则相似；面向资源的设计借鉴了 REST 的许多原则，同时也在适当之处定义了自己的模式。

## 指导

设计 API 时，应考虑以下事项（大致按逻辑顺序排列）：

- API 将提供哪些资源（名词）
- 这些资源之间的关系和层级结构
- 每个资源的模式
- 每个资源提供哪些方法（动词），并尽可能依赖标准动词

### 资源

面向资源的 API **通常应**建模为资源层级结构，其中每个节点要么是简单资源，要么是资源集合。

一个*集合*包含*同一类型*的资源。例如，出版商拥有其出版的图书集合。资源通常包含字段，也可以有任意数量的子资源（通常是集合）。

**注意：** 存储系统和 API 之间虽然存在一定的概念对应关系，但采用面向资源 API 的服务不一定是数据库，在解释资源和方法时拥有很大的灵活性。API 设计者**不应**期待 API 反映数据库模式。事实上，让 API 与底层数据库模式完全一致是一种反模式，因为这会将 API 表面与底层系统紧密耦合。

### 方法

面向资源的 API 强调资源（数据模型），而不是对资源执行的方法（功能）。典型的面向资源 API 会暴露大量资源，而每个资源只有少量方法。这些方法可以是标准方法（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]），也可以是[自定义方法][custom methods]。

如果标准方法（或同一*服务*中的自定义方法）的请求或响应**就是**该资源，或**包含**该资源，那么该资源在所有方法中的资源模式**必须**保持一致。

| 标准方法 | 请求 | 响应 |
| --- | --- | --- |
| Create | 包含资源 | 就是资源 |
| Get | 无 | 就是资源 |
| Update | 包含资源 | 就是资源 |
| Delete | 无 | 无 |
| List | 无 | 包含资源 |

*上表描述了每个标准方法与资源的关系；“无”表示资源既不是请求或响应本身，也不包含在请求或响应中。*

资源**至少必须**支持 [Get][]：客户端必须能够在执行 [Create][]、[Update][] 或 [Delete][] 等变更后验证资源状态。

资源还**必须**支持 [List][]，但无法存在多个资源的[单例资源][singleton resources]除外。

**注意：** 面向资源设计中的自定义方法并不意味着要定义新的或自定义的 HTTP 动词。自定义方法使用传统 HTTP 动词（通常是 `POST`），并在 URI 中定义自定义动词。

API **应**优先使用标准方法而不是[自定义方法][custom methods]；自定义方法用于定义无法清晰映射到标准方法的功能。自定义方法提供了与传统 RPC API 相同的设计自由度，可用于实现数据库事务、导入导出或数据分析等常见编程模式。

### 强一致性

对于操作[管理平面][management plane]的那些方法，操作完成（无论是成功、有错误、长时运行操作还是同步完成）**必须**意味着资源是否存在的状态以及所有用户可设置的值都已达到稳定状态。

与资源[状态][state]无关的[仅输出][output only]值不在此要求之内；但与资源状态相关的值也**应**达到稳定状态。

示例包括：

- 对资源执行成功的创建且这是该资源最近一次变更后，针对该资源的 Get 请求**必须**返回该资源。
- 对资源执行成功的更新且这是该资源最近一次变更后，针对该资源的 Get 请求**必须**返回更新请求中的最终值。
- 对资源执行成功的删除且这是该资源最近一次变更后，针对该资源的 Get 请求**必须**返回 `NOT_FOUND`（使用[软删除][soft delete]时，则返回状态值为 `DELETED` 的资源）。

面向资源的 API 客户端通常需要按顺序编排多个操作（例如创建资源 A，再创建依赖 A 的资源 B）。确保操作完成后资源立即反映稳定的用户状态，可以让客户端依赖方法完成这一信号来开始下一个操作。

[仅输出][output only]字段理想情况下也应遵循相同指导，但这些字段常常表示资源的实时状态，因此成功的变更操作后可能仍需改变这些值，以反映状态变化。

### 无状态协议

与当今大多数公开 API 一样，面向资源的 API **必须**运行在[无状态协议][stateless protocol]之上：任何单独请求的基本行为都独立于调用方发出的其他请求。也就是说，每个请求都与该客户端或其他客户端发出的请求相互隔离，API 暴露的资源可以直接寻址，而不需要先执行一系列特定请求才能“到达”目标资源。

在采用无状态协议的 API 中，服务器负责持久化数据（这些数据可能由多个客户端共享），而客户端独自负责维护应用状态，并拥有维护应用状态的权限。

### 循环引用

资源之间的关系（例如[资源引用][resource references]）**必须**能够通过[有向无环图][directed acyclic graph]表示。父子关系也**必须**是无环的；按照 [AIP-124][] 的规定，一个资源实例只能有一个规范父资源。

资源之间的循环关系会增加资源管理的复杂度。设资源 A 和 B 互相引用，创建它们的过程如下：

1. 创建不引用 B 的资源 A，获取资源 A 的 ID。
2. 创建引用 A 的资源 B，获取资源 B 的 ID。
3. 使用对 B 的引用更新资源 A。

由于需要判断先解除哪个资源的引用才能成功删除，删除操作也可能变得更加复杂。

此要求不适用于通过[仅输出][output only]字段表达的关系，因为用户无需指定这些字段的值，因此不会增加资源管理的复杂度。
