# Unicode

API **应**以一致方式说明、限制并计费字符串值及其编码。这些问题从小的歧义（例如“字段限制为 1024 个字符”）一直延伸到计费困惑（Datastore 中属性的名称和值究竟按字符还是字节计费）。

一般来说，如果使用以字节计量的限制，就会歧视非 ASCII 文本，因为非 ASCII 文本占用更多空间。另一方面，如果使用“字符”，又会产生歧义：这里的字符究竟是 Unicode“码位”、某种编码（例如 UTF-8 或 UTF-16）的“码元”、 “字素”，还是“字素簇”？

## Unicode 入门

字符编码是我们经常略过的领域，下面快速介绍一下：

- 字符串只是按照某种编码格式表示数字的字节。
- 我们说**字符**时，有时指 Unicode **码位**，即 Unicode 规范中的数字（最多 21 位）。
- 有时我们指的是**字素**或**字素簇**，它们可能有多种数字表示，也可能由多个码位表示。例如，`á` 可以由 `U+0061 + U+0301`（`a` 加重音组合标记）组合表示，也可以由单个码位 `U+00E1` 表示。
- Protocol Buffers 使用 **UTF-8**（“Unicode Transformation Format”），这是一种可变长度编码方案，每个码位最多使用 4 个**码元**（8 位字节）。

## 指导

### 字符定义

**简要回答：** 在我们的 API 中，“字符”指“Unicode 码位”。

在 API 文档（例如 API 参考文档、博客文章、营销文档、计费说明等）中，“字符”**必须**定义为 Unicode 码位。

### 长度单位

**简要回答：** 使用“字符”（如上定义）设置大小限制。

API 注释中定义的所有字符串字段长度限制**必须**以字符计量并按字符执行。这意味着底层最大限制为（`4 * 字符数`）字节，但只有在全部使用由 4 个 UTF-8 码元（32 位）组成的字符时才会达到该字节限制。

如果使用允许按字符定义限制的数据库系统（例如 Spanner），可以放心假设底层存储系统会处理这一字节要求。

### 计费单位

API **可以**使用码位或字节（使用 UTF-8 编码）作为计费或配额计量单位（例如 Cloud Translation 选择使用字符）。如果 API 没有定义，默认计费单位是字符（例如每个*字符*收费 $0.01，而不是每个*字节*收费 $0.01）。

### 唯一标识符

**简要回答：** 唯一标识符**应**限制为 ASCII，通常只允许字母、数字、连字符和下划线，且**不应**以数字开头。

用作唯一标识符的字符串**应**将输入限制为 ASCII 字符，通常是字母、数字、连字符和下划线（`[a-zA-Z][a-zA-Z0-9_-]*`）。这样可以避免因规范化导致意外冲突。如果 API 决定允许所有有效 Unicode 字符作为唯一标识符，则**必须**拒绝不属于规范化形式 C 的输入。一般来说，唯一标识符**不应**以数字开头，因为数字前缀保留给 Google 生成的标识符，也能让我们方便判断某个数字 ID 是由我们生成还是由用户选择。

唯一标识符**应**使用最多 64 个字符，不过可以按需扩展。对于大多数场景，64 个字符已经足够，因为即使 UUID 也只需要 36 个字符。

**注意：** 关于资源 ID 片段，请参阅 AIP-122 的建议。

### 规范化

**简要回答：** Unicode 值**应**存储为[规范化形式 C][normalization form c]。

值**应**始终规范化为规范化形式 C。唯一标识符**必须**始终存储为规范化形式 C（见下一节）。

设我们处理西班牙语输入 “estar**é**”（全文中加粗部分均表示重音字符）。这段文本按我们通常的视觉理解包含 6 个“字符”（此处为字素簇）。它有两种可能的 Unicode 表示：

- 使用 6 个码位：`U+0065` `U+0073` `U+0074` `U+0061` `U+0072` **`U+00E9`**
- 使用 7 个码位：`U+0065` `U+0073` `U+0074` `U+0061` `U+0072` **`U+0065` `U+0301`**

进一步编码为 UTF-8 时，这些码位也有两种不同的序列化表示：

- 使用 7 个码元（7 个字节）：`0x65` `0x73` `0x74` `0x61` `0x72` **`0xC3` `0xA9`**
- 使用 8 个码元（8 个字节）：`0x65` `0x73` `0x74` `0x61` `0x72` **`0x65` `0xCC` `0x81`**

为避免大小（码元和码位）出现差异，应使用[规范化形式 C][normalization form c]，它为字符串提供规范表示。

[normalization form c]: https://unicode.org/reports/tr15/

### 唯一性

**简要回答：** 在检查唯一性前，Unicode 值**必须**规范化为[规范化形式 C][normalization form c]。

对于唯一标识（例如 `name`、`id` 或 `parent`），值**必须**规范化为[规范化形式 C][normalization form c]（恰好也是最紧凑的形式）。否则，本质上相同的字符串可能被用来标识两个完全不同的资源。

在上面的示例中，同一段文本本质上有两种表示方式。这引出了一个问题：这两种表示是否应视为等价？换句话说，如果有人将两组字节序列都用于充当唯一标识符的字符串字段，是否会违反唯一性约束？

W3C 建议所有通过互联网传输的内容使用规范化形式 C。它是 Unicode 文本最紧凑的规范形式，可以避免大多数互操作性问题。如果两个 Unicode 字节序列在 NFC 中有相同表示、我们却将它们视为不同，就会被迫在可能的 Get 请求中返回*不符合规范化形式*的内容。这显然不可接受，因此我们**必须**将二者视为相同：把所有输入字符串数据转换为规范化形式 C，或拒绝不是该规范形式的标识符。

关于应将字符串看作由字节表示的码位序列（据此按字符串的字节表示确定唯一性），还是将字符串解释为可以有多种字节表示的更高层抽象，存在一些争论。本文采取的立场是：我们已经有一个字段类型处理前一种情况，即 `bytes`。`string` 类型本身已经表达了对输入有效性的判断（必须是有效 UTF-8）。因此，由于底层字节表示不同，就把规范化形式相同的两个输入视为不同，似乎违背了 `string` 类型的原始意图。对于服务将其视为不透明值的字符串（例如 `description` 或 `display_name`），这种区别通常无关紧要；但当我们依赖字符串唯一标识资源时，就必须明确立场。

换句话说，我们的目标是允许使用任意编码文本（ASCII、UTF-16、UTF-32 等）的用户与 API 交互，而不遇到大量“陷阱”。
