# 批量方法：Update

一些 API 需要允许用户在单个事务中修改一组资源。批量 Update 方法提供了这一能力。

## 指导

API **可以**使用以下两种模式支持 Batch Update：

同步返回响应：

```proto
rpc BatchUpdateBooks(BatchUpdateBooksRequest) returns (BatchUpdateBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:batchUpdate"
    body: "*"
  };
}
```

异步返回解析为响应的 Operation：

```proto
rpc BatchUpdateBooks(BatchUpdateBooksRequest) returns (google.longrunning.Operation) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:batchUpdate"
    body: "*"
  };
  option (google.longrunning.operation_info) = {
    response_type: "BatchUpdateBooksResponse"
    metadata_type: "BatchUpdateBooksOperationMetadata"
  };
}
```

- RPC 名称**必须**以 `BatchUpdate` 开头，名称其余部分**应**是所更新资源的复数形式。
- 请求和响应消息**必须**与 RPC 名称匹配，分别使用 `Request` 和 `Response` 后缀。
- 如果批量方法返回 `google.longrunning.Operation`，则**必须**同时指定 `response_type` 和 `metadata_type` 字段。
- HTTP 动词**必须**是 `POST`。
- HTTP URI **必须**以 `:batchUpdate` 结尾。
- URI 路径**应**表示资源集合，并与简单 CRUD 操作使用的集合一致。如果操作跨越多个父资源，可以接受短横线（`-`）作为通配符。
- `google.api.http` 注解中的 `body` 子句**应**为 `"*"`。

### 原子与部分成功

- 批量 Update 方法**可以**支持原子行为（全部资源更新或一个也不更新）或部分成功行为。选择时应考虑：
  - **确保原子的复杂度：** 简单透传数据库事务**应**使用原子操作，而管理复杂资源的操作**应**使用部分成功操作。
  - **最终用户体验：** 应从 API 消费者角度考虑：即使单个或少数条目导致大批量请求失败，该使用场景是否仍更适合原子行为？
- 同步批量 Update **必须**是原子的。
- 异步批量 Update **可以**支持原子或部分成功。
  - 如果支持部分成功，请遵循[操作元数据消息](#操作元数据消息)的要求。

### 请求消息

批量 Update 方法的请求**应**使用以下模式：

```proto
message BatchUpdateBooksRequest {
  // 所有要更新图书共享的父资源。
  // 格式：publishers/{publisher}
  // 如果设置此字段，UpdateBookRequest 消息中的 parent 字段必须为空
  // 或与该字段匹配。
  string parent = 1 [
    (google.api.resource_reference) = {
      child_type: "library.googleapis.com/Book"
    }];

  // 指定要更新资源的请求消息。
  // 一次批量最多修改 1000 本图书。
  repeated UpdateBookRequest requests = 2
    [(google.api.field_behavior) = REQUIRED];
}
```

- 除非要更新的资源是顶层资源，否则**应**包含 `parent` 字段。如果调用方设置了该字段，而任一要更新资源名称中的父集合不匹配，请求**必须**失败。
  - 如果每个请求只允许一个父资源，该字段**应**为必需。
  - 该字段**应**标识其引用的[资源类型][aip-122-parent]。
  - 字段注释**应**记录资源模式。
- 请求消息**必须**包含一个重复字段，接受按[标准 Update 方法][request-message]指定的更新资源请求消息；该字段**应**命名为 `requests`。
  - 该字段**应**为必需。
- 其他字段**可以**从[标准 Update 请求][request-message]“提升”，即字段可以在批量层级或子请求层级设置。与 `parent` 类似，如果同一字段在两个层级都设置，值**必须**匹配。
  - `update_mask` 字段很适合被提升。
- 请求消息**不得**包含其他必需字段，且除本 AIP 或其他 AIP 描述的字段外，**不应**包含其他可选字段。
- `requests` 字段上方的注释**应**记录允许的最大请求数量。

### 响应消息

批量 Update 方法的响应**应**使用以下模式：

```proto
message BatchUpdateBooksResponse {
  // 已更新的图书。
  repeated Book books = 1;
}
```

- 响应消息**必须**包含一个与已更新资源对应的重复字段。

### 操作元数据消息

- `metadata_type` 消息**必须**以 RPC 名称加 `OperationMetadata` 后缀命名；如果该类型由多个 Batch 方法共享，也可以使用 `Batch` 前缀加 `OperationMetadata` 后缀命名。
- 如果批量 Update 方法支持部分成功，元数据消息**必须**包含 `map<int32, google.rpc.Status> failed_requests` 字段，用于传达部分失败。
  - 映射中的键是批量请求 `requests` 字段中的请求索引。
  - 每个映射项的值**必须**反映单个标准 Update 方法通常返回的错误。
  - 如果失败请求最终可能因服务端重试而成功，则此类暂态错误**不得**通过 `failed_requests` 传达。
  - 如果批量中的所有请求都失败，**必须**设置 `Operation.error`，其中 `code = google.rpc.Code.Aborted`，`message = "None of the requests succeeded, refer to the BatchUpdateBooksOperationMetadata.failed_requests for individual error details"`。
- 元数据消息**可以**包含其他字段来传达操作进度。

### 采用部分成功

已有 Batch API 采用部分成功模式时，**必须**执行以下操作：

- **必须**保留默认行为，以避免不兼容的行为变化。
- 如果 API 返回 Operation：
  - 请求消息**必须**有 `bool return_partial_success` 字段。
  - Operation 的 `metadata_type` **必须**包含 `map<int32, google.rpc.Status> failed_requests` 字段。
  - 请求中的 `bool return_partial_success` 设置为 true 时，API **应**允许部分成功行为；否则继续默认的原子行为。
- 如果 API 同步返回直接响应：
  - 由于现有客户端会将成功响应视为原子操作，API 的现有版本**不得**采用部分成功模式。
  - 应创建新版本，使其返回 Operation，并遵循本 AIP 描述的部分成功模式。

## 设计缘由

### 限制同步批量方法为原子操作

同步批量方法必须原子的限制源于以下考虑。

本 AIP 的上一版建议批量方法必须是原子的。同步响应状态码没有清晰的方式传达部分失败，因为 OK 意味着一切都成功。因此，向响应中增加表示部分失败的新字段会是破坏性变更：现有客户端会将 OK 响应解释为所有资源都已更新。

另一方面，如 [AIP-193](https://aip.dev/193) 所述，Operation 更适合呈现部分状态。Operation 的响应状态码不表达底层操作的结果，客户端必须检查响应体来判断操作是否成功。

### 传达部分失败

本 AIP 建议使用 `map<int32, google.rpc.Status> failed_requests` 字段传达部分失败，其中键是原始批量请求中失败请求的索引。考虑过的其他方案包括：

- `repeated google.rpc.Status` 字段：被否决，因为无法清楚确定每个条目对应哪个请求。
- `map<string, google.rpc.Status>` 字段，键为失败请求的 request id：被否决，因为客户端需要维护 request_id 到请求的映射才能使用部分成功响应；而且，如果服务无法保证单个请求跨多个批量请求的幂等性，为传达错误而填写 request id 可能与 [AIP-155](https://aip.dev/155) 冲突。
- `repeated FailedRequest` 字段，其中 FailedRequest 包含单独的更新请求和 `google.rpc.Status`：被否决，因为在响应中回显请求载荷会增加用户数据敏感性方面的挑战，不值得鼓励。
