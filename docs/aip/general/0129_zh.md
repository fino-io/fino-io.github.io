# 服务端修改值与默认值

服务通常会为资源字段提供默认值，偶尔还会在响应中返回之前对用户输入进行规范化后的值。本文指导说明服务应如何记录这类行为，以便消费者理解。

## 指导

### 单一所有者字段

字段**必须**只有一个所有者，可以是客户端，也可以是服务器。服务器所有的字段**必须**通过 `OUTPUT_ONLY` field_behavior 标明。其他类型的字段**必须**视为客户端所有。服务器**必须**尊重所有客户端所有字段的值（或缺省），不得修改这些字段。

### 有效值

在一些情况下，如果客户端选择不指定值，服务会分配、生成或计算一个值。例如，客户端创建虚拟机时没有指定供虚拟机使用的静态 IP 地址；这表示客户端选择了动态 IP 地址分配。

这类字段的示例包括：

* 生成的值（UUID）
* 分配的值（动态 IP 地址）
* 指定的值（最新的软件包版本）

具有有效值的属性***必须***在 API 中表示为两个字段：

* 一个可变字段，用户可以选择设置，但服务**不得**修改该字段
* 一个 `OUTPUT_ONLY` 字段，记录服务决定的有效值

示例：

```proto
message VirtualMachine {
  …
  string ip_address = 4;
  string effective_ip_address = 5 [
    (google.api.field_behavior) = OUTPUT_ONLY
  ];
}
```

#### 命名

有效值**必须**在可变字段名称前加上 `effective_` 命名。

### 用户指定字段

对于用户指定字段，服务响应中的值**必须**与创建或更新请求提供的值相同。对字符串字段而言，这意味着原样返回值，但有一个例外：

* 如果字符串字段带有数据类型注解，则**可以**返回表示给定值的规范化字符串。

### 规范化

服务规范化的字段**必须**使用 `google.api.field_info` 扩展进行标注。关于该扩展的使用指导，请参见 [AIP-202][]。允许的规范化格式包括：

* uuid
* ipv4
* ipv6
* email

字段上的规范化**必须**使用 `google.api.field_info` 注解进行描述。

## 设计缘由

服务端修改值和默认值通常会让[声明式客户端][]更难实现。对于这些字段，客户端往往无法判断期望状态是否与当前状态相同，因为服务器修改并返回值所遵循的规则复杂、不公开且不可重复。

### 单一所有者字段的设计缘由

字段没有单一所有者时，可能会给[声明式客户端][]带来问题。这些客户端可能会尝试为已被服务器设置值覆盖的字段设置值，从而进入不断纠正变更的无限循环。

### 命名的设计缘由

一致的命名对于识别跨 API 和跨字段的标准行为很重要。用户指定值与有效值之间的程序化关联依赖一致的命名。

### 规范化的设计缘由

规范化让服务能够以标准方式存储和返回值，同时向客户端说明哪些变化在语义上是等价的。在服务端规范化值，可以让服务接受更广泛的、语义相同的输入，而不必将每个值都作为原始字符串维护。向客户端公开所应用的规范化，可以让客户端比较发送值和获取值，从而检查二者是否存在差异。

例如，某资源的一个字段接受电子邮件地址时，客户端可能以多种方式指定同一个地址。对于 `ada@example.com`，客户端可能指定 `ADA@example.com`、`aDa@example.com` 或 `AdA@example.com`。这些值在语义上相同，服务**应**全部接受。服务随后可以通过转为小写或规范化的方式，对电子邮件地址进行存储和获取。重要的是，向客户端公开的字段规范化信息不会描述规范化算法本身，而是描述用于准确计算两个值是否应视为相等的比较方法。

### 字段值处理的设计缘由

对于没有使用允许的规范化方式的字段，[声明式客户端][声明式客户端]将无法识别哪些变化具有语义意义。当[声明式客户端][声明式客户端]发送某个值时，它会确保服务返回该值，以验证值已被正确设置。
