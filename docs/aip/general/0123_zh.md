# 资源类型

大多数 API 都会暴露资源（其主要名词），供用户创建、获取和操作。API 可以相对自由地命名资源类型（在本 AIP 的要求范围内），只需确保类型名在该 API 内唯一。因此，不同 API 使用相同的类型名是可能的，而且通常也是理想的。例如，Memcache API 和 Redis API 都可能希望使用 `Instance` 作为类型名。

然而，在描述 API 与资源之间的关系时，拥有一个全局唯一的类型名就很重要了。此外，Kubernetes 或 GraphQL 等工具会与来自多个提供商的 API 交互。

## 术语

下面的指导使用以下术语：

- **服务名称：** 在[服务配置][service configuration]中定义的名称。它通常（但不一定）与用户调用服务时使用的主机名一致，例如 `pubsub.googleapis.com`。这相当于 Kubernetes 中的 [API Group][]。
- **类型：** API 内用于表示类型的名称，例如 Protobuf `message` 的名称。这相当于 Kubernetes 中的 [Object][]。

## 指导

API **必须**按照 `{Service Name}/{Type}` 模式为 API 中的每个资源定义资源类型。类型名**必须**：

- 与外层 API 类型的名称匹配。
- 以大写字母开头。
- 只包含字母和数字。
- 使用名词的单数形式。
- 使用 PascalCase（UpperCamelCase）。

### 示例

资源类型示例：

- `pubsub.googleapis.com/Topic`
- `pubsub.googleapis.com/Subscription`
- `spanner.googleapis.com/Database`
- `spanner.googleapis.com/Instance`
- `networking.istio.io/Instance`

### 标注资源类型

API **应**使用 [`google.api.resource`][resource] 注解标注 API 中每个资源的资源类型：

```proto
// Pub/Sub 主题的表示。
message Topic {
  option (google.api.resource) = {
    type: "pubsub.googleapis.com/Topic"
    pattern: "projects/{project}/topics/{topic}"
    singular: "topic"
    plural: "topics"
  };

  // 名称及其他字段……
}
```

- 模式**必须**对应[资源名称][aip-122]。
- 模式变量（花括号内的片段）**必须**使用 `snake_case`，且**不得**使用 `_id` 后缀。
- 模式变量**必须**符合 `[a-z][_a-z0-9]*[a-z0-9]` 格式。
- 在一个模式中，模式变量**必须**唯一。（例如 `projects/{abc}/topics/{abc}` 无效；这通常是集合标识符在一个模式内唯一的自然结果。）
- 具有[多个模式][multi-pattern-resources]的资源**必须**保留顺序：新增模式**必须**添加到列表末尾，已有模式**不得**删除或重新排序，否则会破坏客户端库的向后兼容性。
- `singular` **必须**是类型的小写驼峰形式。
  - 模式变量**必须**使用资源类型的单数形式，例如表示 `Topic` 资源 ID 的模式变量应命名为 `{topic}`。
- `plural` **必须**是单数形式的小写驼峰复数。
  - 模式中的集合标识符片段**必须**与资源的复数形式匹配，但[嵌套集合][nested collections]除外。

#### 模式唯一性

资源定义多个模式时，这些模式**必须**彼此唯一。唯一性指：移除所有资源 ID 路径片段、保留所有 `/` 分隔符后，剩余内容必须逐字符不同。

因此，同一资源中**不得**定义以下两个模式：

- `user/{user}`
- `user/{user_part_1}~{user_part_2}`

## 设计缘由

### 类型名与消息名对齐

除了简单的模式与资源一致性及对齐之外，许多使用者也会受益于 `{Type}` 与 `message` 名称保持一致。这样查找更简单，客户端库除了保持一致的用户体验外，也能获得相同的结果：面向资源的代码与生成的 `message` 代码使用一致的命名，生成的参考文档也能将资源与 `message` 文档对应起来，等等。

### 单数与复数

定义清晰的资源单数和复数形式，可以让客户端确定代码和文档中应使用的正确名称。

小写驼峰形式可以转换成资源名称的其他常见形式，例如大写驼峰和蛇形命名法。
