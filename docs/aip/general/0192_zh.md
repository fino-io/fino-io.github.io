# 文档

文档是 API 设计最关键的部分之一。用户无法直接阅读实现，API 定义和文档往往是他们理解服务的全部依据，因此文档必须清晰、完整且无歧义。

## 指导

Proto API 的每个公共组件（service、method、message、field、enum 和 enum value）**必须**有 protobuf 格式的公共注释。服务注释尤其应说明服务的职责以及用户可以做什么。

### 风格

文档应使用完整句子、主动语态和一致术语；首句应概括被注释组件。避免实现细节、内部缩写和“显然”“简单”等假设读者已有背景的措辞。

### 描述

资源字段应说明格式、单位、默认值、可变性和权限要求；方法应说明输入、输出、副作用、错误和一致性；枚举值应说明语义，不应只重复名称。

### 格式

使用 Markdown/Proto 注释支持的格式，代码、字段名、资源名称和错误码使用反引号。列表和表格应保持可读，长段落应拆分。

### 交叉引用

相关 AIP、资源、方法和字段应使用可访问的链接。链接文本应说明目标，不要只写“点击这里”。引用外部规范时应链接到权威来源。

### 外部链接

外部链接应稳定、必要并指向官方文档；链接失效或内容移动时应及时更新。不要把临时 issue、内部页面作为唯一规范来源。

### 商标名称

首次出现时遵循商标所有者的正式写法；不要把品牌名当作通用 API 概念，也不要在字段和方法名中引入不必要的品牌绑定。

### 弃用

弃用组件的注释必须说明弃用原因、替代方案和迁移时间；保留现有语义，不能只删除文档而让客户端无法判断如何迁移。

### 内部注释

实现注释可以保留在源码中，但不得出现在生成的公共 API 文档中，也不能用内部链接或敏感信息污染公共注释。
