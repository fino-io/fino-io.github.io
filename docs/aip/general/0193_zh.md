# 错误

有效的错误通信是简单、直观 API 的重要组成部分。标准化错误响应让客户端能够构建统一的错误处理逻辑，减少繁琐的自定义代码。

## 指导

API 出错时服务**必须**返回 [`google.rpc.Status`][Status]，并使用 [`google.rpc.Code`][Code] 中定义的规范错误码。错误消息应帮助具备一般技术能力的用户理解并解决问题，不能假设用户熟悉具体 API 或底层实现。

### Status.message

`Status.message` 是面向开发者的可读说明，应简洁、可操作，并可包含请求相关细节。机器可解析的信息必须放在 `details` 的结构化消息中，不能要求客户端解析 message 文本。

### Status.code

服务必须使用最匹配语义的规范码，例如参数无效使用 `INVALID_ARGUMENT`，资源不存在使用 `NOT_FOUND`，无权访问使用 `PERMISSION_DENIED`，并发版本冲突使用 `ABORTED`。不要用 `UNKNOWN` 或 `INTERNAL` 代替可表达的具体错误。

### Status.details

`details` 可以包含结构化错误信息：

#### ErrorInfo

`google.rpc.ErrorInfo` 提供 reason、domain 和 metadata，适合让客户端根据稳定 reason 和键值采取动作。metadata 不应包含秘密或完整用户数据。

#### LocalizedMessage

需要本地化时可以加入 `google.rpc.LocalizedMessage`。机器逻辑仍应依赖 code、reason 等稳定字段，不应依赖翻译后的文本。

#### Help

`google.rpc.Help` 可以提供帮助文档链接；链接应指向能解决当前问题的页面，而不是通用首页。

### 错误消息

消息应说明发生了什么、涉及哪个资源或字段，以及用户下一步可以做什么。不要泄露不存在资源的敏感信息，也不要把堆栈、内部主机名、令牌或密钥写入响应。

#### 更改错误消息

如果 RPC 始终返回带机器可读信息的 `ErrorInfo`，`Status.message` 可以改进措辞；否则应保持稳定，避免客户端依赖的文本突然变化。需要变更时，可在 `Status.details` 增加 `LocalizedMessage`，而不要改变旧文本的含义。

### 部分错误

批量方法可以成功处理部分项目；响应必须同时提供总体状态和逐项错误。不要用一个总体错误丢失已成功或失败项目的信息。

### Permission Denied

用户无权访问资源时必须返回 `PERMISSION_DENIED`（HTTP 403），而不是根据资源是否存在返回 `NOT_FOUND`，否则会泄露资源存在性。服务应先进行权限检查，再进行存在性检查。只有拥有访问权限但资源不存在时才返回 `NOT_FOUND`（HTTP 404）。

## HTTP/1.1+JSON 表示

HTTP+JSON 客户端应收到与 gRPC 语义对应的 HTTP 状态码以及 JSON 编码的 `google.rpc.Status`。`code`、`message` 和 `details` 应保持一致，代理不得把结构化错误改写为无意义的纯文本。

## 设计缘由

要求 `ErrorInfo` 等结构化详情，是为了让客户端在不解析自然语言的情况下采取动作；`LocalizedMessage` 用于用户界面，而不是机器决策；保持 `Status.message` 稳定可以兼容尚未迁移到结构化详情的旧客户端。
