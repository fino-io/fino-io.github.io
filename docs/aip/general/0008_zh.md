# AIP 风格与指导

AIP 是 **API Improvement Proposal**（API 改进提案）的缩写，是一类为 API 设计与开发提供高层次、简明说明的设计文档。AIP 的目标是成为 API 相关文档的事实来源，也成为 API 团队讨论 API 指导并达成共识的依据。

AIP 最有价值的特征是清晰、简洁，并且聚焦于一个主题或问题。正如 AIP 描述 API 中一致的模式与风格一样，AIP 本身也应遵循一致的结构与风格。

## 指导原则

- AIP **必须**围绕单一、明确的主题，并提供清晰、可执行的指导。
- AIP **不得**重复或违背其他 AIP 中的指导。
- AIP **可以**说明不应采用的做法，但**不应只**描述反模式。
- 如果 AIP 的指导具有条件性（例如 Jobs 这样的设计模式），必须清楚说明在什么条件下应遵循该指导。

AIP 中的指导必须至少对一种客户端或其作者有益，包括但不限于：

- 可用于审计和分析资源的资产清单；
- 用于探索和简单自动化的命令行界面；
- 轮询实时状态并调整资源配置的自定义控制器（例如自动伸缩器）；
- 用于编排和自动化多个资源的 IaC 客户端；
- 为特定场景推荐有用 API 及其用法的推荐工具；
- 使用某种编程语言与 API 交互的 SDK，通常大量用于数据面操作；
- 安全编排、自动化与修复工具；
- 用于自动化或编排任务的简单脚本；
- 测试框架；
- 处理静态资源数据的工具；
- 用于可视化和一次性手动操作的图形界面；
- 用户。

改进的例子包括：要求新增 proto 注解，使客户端能够获得更具描述性的接口（例如在 `google.api.resource` 注解中要求提供 `singular` 和 `plural`）。

AIP 指导不得显著损害客户端的可用性、实现难度或维护难度。例如，不应在标准方法中引入非统一模式，导致所有客户端都必须增加额外代码，却得不到足够收益；也不应为了轻微提升可读性而重命名已经广泛使用的字段。

AIP 长度会随问题复杂度而变化，但大多数 AIP 应能在大约两页打印纸内完整说明其内容。

### 文件结构

AIP **必须**使用 Markdown 编写，并以四位编号命名（例如 `0008.md`）。针对特定 Scope 的 AIP **必须**放在该 Scope 的子目录中。

AIP **必须**包含适当的 front matter，例如：

```yaml
---
id: 8
state: reviewing
created: 2019-05-28
permalink: /8
redirect_from:
  - /08
  - /008
  - /0008
---
```

front matter **必须**包含：

- `id`：必填，AIP 编号，整数。
- `state`：必填，当前状态，使用小写形式；常见值为 `draft`、`reviewing`、`approved`。
- `created`：必填，AIP 首次起草日期，使用 ISO-8601 的 `yyyy-mm-dd` 格式。
- `updated`：可选，最近一次修订日期。
- `scope`：AIP 的 Scope。必须与 Scope 目录名一致；编号大于等于 1000 的 AIP 必填，其他 AIP 禁止填写。

`permalink` 必填：如果没有 Scope，应为 `/{id}`；有 Scope 时应为 `/{scope}/{id}`。`redirect_from` 可以列出读者可能输入的其他编号形式，包括不补零、补一到三位零的形式。

### 文档结构

AIP **必须**以顶级标题开始，标题应为 AIP 的标题（`# Title`），并且最好使用名词而不是祈使句。标题之后应直接是引言，然后是 `## Guidance`。必要时可按以下顺序包含：

- **Further reading：** 帮助理解当前 AIP 的其他 AIP 链接列表；
- **Appendices：** 对当前 AIP 的补充说明；
- **Changelog：** 自首次编写以来的变更列表。

指导部分可以使用子章节展开细节。除标题外，AIP **只能**使用二级及以下标题，通常只使用 `##` 和 `###`。

### 要求级别关键词

AIP **应**使用以下要求级别关键词：`MUST`、`MUST NOT`、`SHOULD`、`SHOULD NOT`、`MAY`。它们的含义按 RFC 2119 解释。使用这些术语时，必须使用小写并加粗，并且不得以其他方式使用。

如果使用 `SHOULD` 或 `SHOULD NOT`，必须给出其他因素可能覆盖该指导的有效示例。重要的是，Rationale 只用于提供背景和更完整的理解，不得包含指导，也不得使用 RFC 2119 要求关键词。

### 代码示例

API 设计示例**应**使用 Protocol Buffers，并且只包含解释概念所需的最少语法。在 RPC 示例中，**应**包含 `google.api.http` 注解。

### 引用 AIP

引用其他 AIP 时，正文**必须**使用不补零的 `AIP-XXXX` 格式（例如 `AIP-8` 而不是 `AIP-0008`），并链接到相关 AIP。AIP 链接**必须**使用仓库中的相对文件路径（核心 AIP 如 `./0008.md`，Scope 子目录中的 AIP 如 `../0008.md`），以确保链接在网站、GitHub、开发服务器和分支环境中都能工作。

## 设计缘由

### 面向广泛的客户端

API 指导与其他软件一样，只有在目的明确、受益对象明确时才最有价值。改进 API 设计的受益者是用户，而用户会根据场景使用不同类型的客户端。因此，API 指导也必须广泛考虑这些客户端的影响。
