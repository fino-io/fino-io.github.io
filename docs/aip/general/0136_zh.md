# 自定义方法

面向资源的设计（AIP-121）使用自定义方法表达仅靠标准方法难以建模的任意操作。自定义方法让 API 词汇能够贴合用户意图。

## 指导

只有无法轻易用标准方法表达的功能才**应**使用自定义方法；只要语义适用，就应优先使用标准方法。

```proto
// 归档指定的图书。
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

自定义方法可以关联资源、集合或服务，以下原则适用于三种情况：

- 方法名**应**是“动词 + 名词”，不得包含介词（如 `for`、`with`），动词**不应**使用标准方法动词（[Get][]、[List][]、[Create][]、[Update][]、[Delete][]）。名称不得包含 `Async`；需要区分即时和长时运行 RPC 时，可以使用 `LongRunning` 后缀。
- HTTP 方法**必须**是 `GET` 或 `POST`：读取数据或资源状态使用 `GET`；请求体可能超过 URL 限制时，读取操作也可以使用 `POST`；存在副作用或修改数据时必须使用 `POST`。
- HTTP URI **必须**使用 `:` 加自定义动词（例如 `:archive`），且 URI 中的动词必须与 RPC 名称一致；需要分隔词时必须使用 `camelCase`。
- `google.api.http` 注解的 `body` **应**为 `"*"`。
- 请求和响应消息**应**分别以 RPC 名称加 `Request`、`Response` 命名；操作特定资源时，响应可以直接是该资源。

### 基于资源的自定义方法

如果 API 可以建模为资源，自定义方法**必须**作用于资源：

```proto
rpc ArchiveBook(ArchiveBookRequest) returns (ArchiveBookResponse) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:archive"
    body: "*"
  };
}
```

资源名称参数**必须**命名为 `name`，并且是 URI 路径中的唯一变量。

### 基于集合的自定义方法

少数自定义方法可以作用于集合：

```proto
rpc SortBooks(SortBooksRequest) returns (SortBooksResponse) {
  option (google.api.http) = {
    post: "/v1/{parent=publishers/*}/books:sort"
    body: "*"
  };
}
```

集合有父资源时，父资源字段**必须**命名为 `parent`，并且是路径中的唯一变量；集合键（上例中的 `books`）必须是字面量。

### 无状态方法

不附加到资源的自定义方法通常是无状态的：接收请求、返回响应，并且不会永久影响 API 中的数据。

```proto
rpc TranslateText(TranslateTextRequest) returns (TranslateTextResponse) {
  option (google.api.http) = {
    post: "/v1/{project=projects/*}:translateText"
    body: "*"
  };
}
```

若方法在特定范围内运行，请求字段**应**使用该范围资源的名称；需要分隔词时必须使用 `snake_case`。URI 中动词和名词都**应**放在冒号后（如 `:translateText`，而不是 `text:translate`）。涉及计费时，无状态方法**必须**使用 `POST`。

### 声明式友好资源

声明式友好资源通常**不应**使用自定义方法，因为声明式工具无法自动判断应如何处理它们。Move、Rename 等罕见且本质上命令式的操作可以例外。

## 设计缘由

资源或集合方法需要 `name` 或 `parent` 参数，以明确操作对象，使客户端能够将方法映射到相应资源。允许 `GET` 与 `POST` 可以清楚地区分无副作用读取和会修改数据的操作；读取操作必要时使用 POST 还可以避免 URL 过长、统一序列化方式，并容纳复杂请求数据。

方法名中使用介词通常意味着应该向既有方法增加字段，或应该选择另一个明确动词。例如，与其使用 `CreateBookFromDictation`，不如使用 `TranscribeBook`；与其使用 `GetBookByAuthor`，不如使用带 `author` 搜索维度的 `SearchBooks`。这样可以避免 API 表面出现大量过于专门的方法。

`async` 表示编程语言层面的同步/异步调用，与 RPC 是否启动长时运行操作属于不同抽象层级；将其放入 RPC 名称会造成混淆，甚至影响生成同步与异步客户端方法。

## 变更记录

- **2026-06-09：** 必要时允许将复杂 GET 请求改为 POST。
- **2025-05-12：** 扩展禁止在方法名中使用介词的设计缘由。
- **2023-05-16：** 禁止在 RPC 名称中使用 `async`。
- **2023-05-09：** 增加 GET/POST 指导，并要求使用 `parent`。
- **2023-03-02：** 明确不建议使用标准方法动词。
