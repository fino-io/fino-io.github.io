# API 专用 proto

API 主要由 API 专用的 proto 定义，偶尔依赖通用组件。让 API 相互隔离，可以避免版本管理和客户端库打包问题。

## 指导

- API 专用的所有 proto **必须**位于带主版本的包中（例如 `google.library.v1`）。
- 对其他 API 中资源的引用**必须**使用资源名称（[AIP-122][]）表达，而不是使用资源消息。
- 如果 API 的两个版本使用实质相同的（API 专用）proto，那么该 proto **必须**在每个版本中复制。（换句话说，API **不得**创建自己的“API 专用通用组件”包。）
- 组织专用的通用组件**可以**放在通用包中，如 [AIP-213][] 所述，但**不得**被该组织之外的 API 使用。
- 全局通用组件（同样见 AIP-213）**可以**被任意 API 自由使用。

## 设计缘由

一个 API 依赖另一个 API 定义的 proto 时，会给客户预期的行为和客户端库依赖管理带来不确定性。假设 `google.cloud.library.v1` 依赖 `google.cloud.movies.v2` 中的 proto（而不是抽象资源）。`google.cloud.movies.v2` 的任何变化都可能造成问题。

例如：

- 如果向 `google.cloud.movies.v2` 的消息添加字段，使用 `google.cloud.library.v1` 的客户是否应当看到它？如果应该，字段添加后多久能看到？其他 API 变化又如何处理？
- 如果整个主版本 `google.cloud.movies.v2` 被弃用（通常是在 v3 发布后），这是否意味着 `google.cloud.library.v1` 必须改为使用 `google.cloud.movies.v3`？如果是，是否也需要为 library API 创建新的主版本？
- 客户端库的版本管理应如何反映被依赖 API 的变化？

让 API 彼此隔离，只共享少量以高度严谨方式维护的通用组件，可以减少许多依赖问题。

跨版本共享 API 专用通用组件会增加客户端库生成和打包的复杂度，而且在版本管理方面不够灵活。即使多个版本最初因为相同而复制 proto，隔离后它们仍然可以随时间各自演进。
