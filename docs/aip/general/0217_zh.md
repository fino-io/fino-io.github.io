# 不可达资源

有时，用户会请求资源列表，其中一部分资源暂时不可用。最典型的场景是支持[跨集合读取][aip-159]。例如，用户可能请求跨多个父位置列出资源，但其中某个位置暂时不可达。此时，仍然希望向用户提供所有可用资源，同时说明有资源缺失。

## 指导

如果获取数据的方法可能因为一个或多个资源暂时不可达而部分失败，响应消息**必须**包含一个字段来表示这一点：

```proto
message ListBooksResponse {
  // 匹配请求的图书。
  repeated Book books = 1;

  // 如果还有匹配请求的图书，则为下一页令牌。
  string next_page_token = 2;

  // 不可达资源。
  repeated string unreachable = 3 [
    (google.api.field_behavior) = UNORDERED_LIST
  ];
}
```

- 字段**必须**是重复字符串，且**应**命名为 `unreachable`。
- 字段**必须**包含不可达资源的资源名称，或阻碍访问请求集合的资源名称，例如无法访问的集合的父资源。
  - 例如，如果整个位置不可达，导致无法访问请求的本地化资源集合，则应包含该位置资源。
- 字段**必须**包含服务相对资源名称，**不得**包含完整资源名称、资源 URI 或简单资源 ID。定义请参阅 [AIP-122][aip-122]。
  - 例如，如果 `Book` 资源不可达，则 `unreachable` 中应包含服务相对资源名称 `"shelves/scifi1/books/starwars4"`，而不是完整资源名称 `"//library.googleapis.com/shelves/scifi1/books/starwars4"`、相对父资源的名称 `"books/starwars4"`、资源 ID `"starwars4"` 或资源 URI。
- 响应**不得**提供导致列出的资源不可达的问题的任何其他信息。
  - 例如，响应不能为每个 `unreachable` 条目添加包含错误原因的额外字段。
- 服务**必须**提供一种方式，让用户发起更具体的请求并接收包含额外信息的错误，例如对不可达集合的父资源执行标准 Get 或标准 List。
  - 服务**还必须**允许用户使用更严格的参数重复原始调用。
- `unreachable` 中出现的资源名称**可以**是异构的。
  - `unreachable` 字段定义**应**记录该字段可能提供哪些资源，并说明未来可能扩展。
  - 例如，如果整个位置以及另一个位置中的特定资源都不可达，则不可达位置的名称（如 `"projects/example123/locations/us-east1"`）和不可达资源的名称（如 `"projects/example123/locations/europe-west2/instances/example456"`）都会出现在 `unreachable` 中。
- `unreachable` 列表中的资源名称**不得**具有语义上的顺序或结构。换句话说，`unreachable` **必须**是无序列表。
  - 因此，`unreachable` 字段**必须**标注 `UNORDERED_LIST` 字段行为（参见 [AIP-203][unordered]）。

**重要：** 如果单个不可达的位置或资源按定义会阻止返回任何数据（例如，针对单个出版商的 List 请求中该出版商不可达），服务**必须**以错误失败整个请求。

### 分页

服务准备一页结果以满足分页获取 RPC（例如 [AIP-132][aip-132] 标准 List 调用）时，如果遇到不可达资源或集合，**必须**执行以下操作：

- 在 `unreachable` 响应字段中包含不可达资源的资源名称。
  - 资源名称**必须**使用最适合不可达资源或集合的范围。
    - 例如，如果某个区域内的特定可用区不可达，则不可达资源名称应是可用区 Location，例如 `projects/example/locations/us-west1-a`；但如果整个区域不可达，则应是区域 Location，例如 `projects/example/locations/us-west1`。
  - 无论分页参数是否具有限制（例如 `order_by`），只要识别出资源不可达，就**必须**包含该资源名称。
- 如果之前被视为不可达的资源恢复可用，且分页参数允许包含它们，则在后续页面填充这些资源。
  - 根据分页参数确定是否有资格包含资源，也包括请求未指定排序时任何已记录的默认排序行为。
  - 例如，如果有序分页调用的第一页中 `projects/example/locations/us-west1` 不可用，且包含其资源会违反排序，则下一页不包含这些乱序资源。
  - 同样，如果发出完全相同的请求，而之前不可达的资源重新可用，则在分页参数约束范围内，**必须**填充这些资源。
- 如果即使扩大不可达资源名称的范围后，不可达资源名称数量仍超过已记录的最大值，则限制单个响应返回的不可达资源名称数量。
  - 该最大值**必须**直接记录在 `unreachable` 字段注释中。
  - 该上限与调用方设置的 `page_size` 无关。

#### 保留之前的行为

如果改变服务已实现的 `unreachable` 分页行为会根据 [AIP-180][aip-180] 造成不兼容变更，服务**可以**继续使用之前的行为，但**必须**直接在 `unreachable` 字段中记录该行为。

### 采用部分成功

如果已有 API 的默认行为与上述指导不同（即 API 调用返回错误状态，而不是部分结果），要采用 `unreachable` 模式，API **必须**执行以下操作：

- **必须**保留默认行为，以避免不兼容的行为变化。
  - 例如，如果默认行为是任一位置不可达就返回错误，则**必须**保留该默认行为。
- 请求消息**必须**有 `bool return_partial_success` 字段。
- 响应消息**必须**有标准的 `repeated string unreachable` 字段。
- 上述两个字段**必须**同时添加。

请求中的 `bool return_partial_success` 字段设置为 `true` 时，API **必须**按照上述指导填充 `repeated string unreachable` 响应字段。

```proto
message ListBooksRequest {
  // 标准 List 请求字段……

  // 将此字段设为 `true`，请求将选择返回可达资源，
  // 并在 [ListBooksResponse.unreachable] 字段中包含不可达资源名称。
  // 只有跨集合读取时才能设为 `true`，例如 `parent` 设置为
  // `"projects/example/locations/-"` 时。
  bool return_partial_success = 4;
}

message ListBooksResponse {
  // 标准 List 响应字段……

  // 不可达资源。当请求选择 `return_partial_success`，
  // 并跨集合读取（例如尝试列出所有支持位置中的所有资源）时填充。
  repeated string unreachable = 3 [
    (google.api.field_behavior) = UNORDERED_LIST
  ];
}
```

#### 部分成功粒度

如果请求中的 `bool return_partial_success` 设置为 `true`，但请求范围超出了 API 能够合理报告不可达资源的支持粒度，API **应**返回 `INVALID_ARGUMENT` 错误，并在详细信息中说明问题。例如，如果 API 只在[跨集合读取][aip-159]时支持 `return_partial_success`，那么当请求范围是特定父资源集合时，应返回 `INVALID_ARGUMENT` 错误。支持的粒度**必须**记录在 `return_partial_success` 字段中。

## 设计缘由

### 使用服务相对资源名称

通常，AIP-122 定义的相对资源名称，是在服务内部按名称引用资源，以及在另一个服务明显可知时跨服务引用资源的最佳实践。完整资源名称格式可消费性严格更低（例如需要客户端额外解析），且对 `unreachable` 的使用来说信息过度。资源 URI 不是传输无关的：gRPC 用户无法在标准方法中使用它；简单资源 ID 也无法在异构资源列表中提供足够信息来确定哪个资源不可达。

### 减少响应中的额外错误信息

发现不可达资源的上下文可能敏感，而且系统状态会在调用之间变化。因此，最好让服务通过针对具体资源或父资源的更具体 RPC 来提供详细信息。这样父资源可以在请求发生时处理所有必要的 RPC 检查和系统状态解析，而不必把可能受权限保护或已经过时的信息硬塞进更宽泛的列表调用中。

### `unreachable` 内容无序

为了保持 API 的广泛一致性，`unreachable` 内容不应具有特定的顺序或结构语义。如果每个 API 都为标准字段固化一种具体排序，就不会存在一个客户端或服务器端实现可以正确适用于所有 API。

### 按页返回 `unreachable` 资源

按页填充 `unreachable` 资源，能让最终用户立即发现某一页不完整，而不是在遍历全部结果后才发现。分页到完成并无保证，因此尽快告知某一页中存在不可达资源很重要。此外，这还允许用户识别后续调用需要处理的潜在问题。将不可达资源保留到分页结束，则要求服务保留本应相互独立、完全隔离的 API 调用状态。

### 使用请求字段选择加入

引入新的请求字段来选择部分成功行为，是表达用户意图并保持默认行为向后兼容的最佳方式。另一种方案是随着引入 `unreachable` 响应字段改变默认行为，这会产生向后不兼容变更。之前预期任一资源不可达时请求失败的用户，可能会把成功响应理解为所有资源都已包含在响应中。

### 同时引入字段

同时引入请求字段和响应字段，是为了避免只添加其中一个而呈现无效的中间状态。如果只添加 `unreachable`，用户可能认为它为空就意味着返回了所有资源，但实际不一定如此。如果只添加 `return_partial_success`，用户又无法知道哪些资源不可达。

### 部分成功粒度的限制

在某个请求范围粒度下，API 可能根本无法枚举不可达资源。例如，仅支持全局范围的 API 可能无法在本地化集合层级提供粒度。在这种情况下，当 `return_partial_success=true` 时预先返回错误，可以保护用户免受另一种风险：他们期待在出现问题时得到不可达资源，但实际没有得到，于是错误地认为一切资源都已获取。这与本文建议主动失败无法完成的请求的指导一致。

## 历史

### 分页指导

最初关于如何填充 `unreachable` 字段的指导，是将其内容视作分页结果来消费。这意味着分页资源和不可达资源不能在同一响应（即同一页）中返回，用户必须完整遍历所有结果才能发现是否存在不可达资源。变更理由见“设计缘由”章节。
