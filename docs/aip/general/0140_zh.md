# 字段名称

直观地命名字段往往是 API 设计中最困难的工作之一。同一公司在不同 API 中用不同名称表示同一概念，或用同一名称表示不同概念，会让用户无法复用既有知识。字段名应简单、直观且彼此一致。

## 指导

字段名**应**使用正确的美式英语，准确表达概念，避免含义宽泛或不必要的修饰词，并考虑生成客户端 API 的可读性和长度。

### 大小写

Proto 字段**必须**使用 `lower_snake_case`。每个单词不得以数字开头，也不得包含开头、结尾或相邻的下划线。

### 统一性

同一概念尽量使用同一名称，不同概念使用不同名称，尤其是可能一起使用的 API 之间。

### 重复字段

重复字段**必须**使用正确的复数形式，如 `books`、`authors`；非重复字段**应**使用单数形式，如 `book`、`author`。资源名称也应使用单数形式。

### 介词

字段名**不应**包含 `with`、`for`、`at`、`by` 等介词，例如使用 `error_reason` 而不是 `reason_for_error`，使用 `author` 而不是 `written_by`。`per` 是表示单位的例外，详见 [AIP-141][]。

### 缩写

软件开发者熟知的缩写**应**直接使用：`config`、`id`、`info`、`spec`、`stats`，而不是完整拼写。单位也应使用通用缩写，如 `distance_km`、`width_px`。

### 形容词与动词

同时包含形容词和名词时，形容词**应**放在名词前，如 `collected_items` 而非 `items_collected`。字段名**不得**表达意图或动作，必须使用名词，如 `disabled` 而非 `disable`；方法名才使用动词。

### 布尔值

布尔字段**应**省略 `is` 前缀，如 `disabled` 而不是 `is_disabled`。如果省略后会与保留字冲突，可以保留，例如 `is_new`。

### string 与 bytes

JSON 在线传输 `bytes` 时会自动使用 Base64。需要传输二进制内容时**应**使用 `bytes`，不应要求用户把内容手工编码到 `string`。若数据本身需以 Base64 形式存储，使用 `bytes` 会造成不必要的双重编码，此时可以使用 `string`。

### URI

表示任意 URI 的字段**应**命名为 `uri`；URL 是 URI 的子集，但 URI 不一定是 URL。只能表示 URL 时**应**使用 `url`，可以按需要加前缀。

```proto
message Book {
  string name = 1 [(google.api.field_behavior) = IDENTIFIER];
  string image_url = 2;
  string uri = 3;
}
```

### 保留字与冲突

字段名**应**避免 `new`、`class`、`function`、`import` 等常见编程语言保留字。消息不应包含与外层消息同名（忽略大小写转换）的字段，以免生成某些语言的代码时冲突。

### 显示名称

面向用户界面的可读名称**应**命名为 `display_name`，且不应要求唯一。实体有正式名称（如公司名称或书名）时，可以使用 `title`；该字段也不应要求唯一。

## 设计缘由

所有 URL 都是 URI，但并非所有 URI 都是 URL。优先使用更通用的 `uri` 可以覆盖更多场景并促进跨 API 标准化；`should` 的要求也为确实需要更具体术语的场景保留了空间。
