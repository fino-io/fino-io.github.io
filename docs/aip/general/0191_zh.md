# 文件与目录结构

一致的文件和目录结构虽然对技术行为影响不大，却能让 API 定义更容易阅读、评审和维护。以下指导主要适用于 Protocol Buffers。

## 指导

### 语法

Proto API **必须**使用 `proto3` 语法。

### 单一 package

一个 API 版本**应**使用单一 protobuf package；package 应包含组织域名、产品域和 major 版本，例如 `library.v1`。不同 major 版本使用不同 package。

### 文件名

文件名**应**使用小写 `snake_case`，并按主题划分，例如 `books.proto`、`book_service.proto`。避免一个文件混合无关资源，也避免为每个消息创建过多小文件。

### 文件布局

文件通常按以下顺序组织：版权和语法、package、import、选项、服务、资源消息、请求/响应消息、枚举及辅助消息。公共服务和消息应放在稳定、可预测的文件中。

### 打包注解

Java、Go 等语言的生成包选项应与 protobuf package 一致且稳定。包选项改变会破坏生成客户端；应在首次发布时确定，并为不同版本明确设置。

## 设计缘由

统一结构降低新用户理解 API 的成本，也让工具可以按约定发现服务、资源和请求消息。Java package、Go package 等语言选项应服务于生成代码体验，不能反过来驱动 API 的资源层次。
