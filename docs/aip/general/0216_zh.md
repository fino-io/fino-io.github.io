# 状态

许多 API 资源都包含“状态”的概念，通常表示资源在其生命周期中的位置。例如，虚拟机可能正在配置、可供使用、正在停止，或者处于其他若干状态之一。作业或查询可能正在准备运行、正在运行、已经完成，等等。

## 指导

需要表达状态的资源**应**使用枚举，该枚举**应**称为 `State`（如果需要更具体的名称，则应以 `State` 结尾）。当枚举只作为该消息中的字段使用时，它**应**嵌套在所描述的消息中。

**重要：** 我们使用 `State` 一词，而*不*使用 `Status`；`Status` 保留给 HTTP 和 gRPC 状态。

### 枚举值

理想情况下，Google API 在表达相同语义概念时应始终使用相同术语。表达某一状态通常有很多可选词汇，但客户经常组合使用多个 API，术语一致会让他们更容易理解。

高层次上：

- 可供使用的资源是 `ACTIVE`（优先于 “ready” 或 “available” 等术语）。
- 已完成请求操作（通常是终态）的资源使用过去分词（通常以 `-ED` 结尾），例如 `SUCCEEDED`（而非 “successful”）、`FAILED`（而非 “failure”）、`DELETED`、`SUSPENDED` 等。
- 正在经历状态变化的资源使用现在分词（通常以 `-ING` 结尾），例如 `RUNNING`、`CREATING`、`DELETING` 等。此时通常意味着该状态是临时的，会自行解析为另一个状态，不需要用户进一步操作。

**注意：** 只添加对客户有用的状态。仅因为内部系统存在大量状态就全部暴露出来没有必要，反而会使客户困惑。每个状态都必须有说明其必要性的使用场景。

### 仅输出

资源中引用 `State` 枚举的字段**应**按照 [AIP-203](./0203.md) 的要求，表现为并记录为“仅输出”。

API **不应**允许通过 `update` 方法直接更新 `State` 枚举（也不应通过 `create` 方法直接设置），而**应**使用状态转换自定义方法。

这是因为通常不希望更新方法产生副作用；直接更新状态还意味着可以将状态设置为任意可用值，而状态通常反映资源在生命周期中的推进过程。

### 状态转换方法

状态转换方法是一种特殊的自定义方法，负责将状态字段从一个枚举值转换为另一个枚举值。转换过程中也可能改变其他字段，例如 `update_time`。方法定义应如下所示：

```proto
// 发布一本图书。
// 发布后图书的 `state` 为 `PUBLISHED`。
// `PublishBook` 可以对处于 `DRAFT` 状态的 Book 调用；
// 对处于其他状态（包括 `PUBLISHED`）的 Book 调用会返回错误。
rpc PublishBook(PublishBookRequest) returns (Book) {
  option (google.api.http) = {
    post: "/v1/{name=publishers/*/books/*}:publish"
    body: "*"
  };
}
```

- 方法名称**应**由动词加资源消息名称的单数形式组成。
- 请求消息**必须**与 RPC 名称匹配，并带有 `Request` 后缀。
- 响应消息**应**是资源本身。
  - 如果 RPC 是[长时运行操作][long-running]，响应消息**应**为解析到资源本身的 `google.longrunning.Operation`。
- HTTP 动词**必须**是 `POST`。
- HTTP URI **必须**使用 `:` 字符加自定义动词（上例为 `:publish`），且 URI 中的动词**必须**与 RPC 名称中的动词一致。
  - 如果需要分隔单词，**必须**使用 `camelCase`。
- `google.api.http` 注解中的 `body` 子句**必须**是 `"*"`。
- 接收资源名称的请求消息字段**应**映射到 URI 路径。
  - 该字段**应**称为 `name`。
  - `name` 字段**应**是 URI 路径中的唯一变量。其余参数**应**映射到 URI 查询参数。
- 如果不允许状态转换，服务**必须**返回 `FAILED_PRECONDITION`（HTTP 400）。

请求消息应如下所示：

```proto
message PublishBookRequest {
  // 要发布的图书名称。
  // 格式：publishers/{publisher}/books/{book}
  string name = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      type: "library.googleapis.com/Book"
    }];
}
```

- **必须**包含资源名称字段，且**应**称为 `name`。
- 字段注释**应**记录资源模式。
- **可以**包含其他字段。

## 其他指导

### 默认值

每个状态枚举的零值**应**遵循以下约定：

```proto
enum State {
  // 默认值。省略状态时使用此值。
  STATE_UNSPECIFIED = 0;

  // 其他值……
}
```

资源**不应**向用户提供未指定状态，该值实际上也**不应**被使用。

### 值的唯一性

同一包中的多个顶层枚举**不得**共享相同的值。这是因为 C++ protoc 代码生成器会将顶层枚举值展平到同一命名空间。

状态枚举**应**位于资源定义内部。

### 前缀

为每个枚举值使用 `STATE_` 前缀没有必要。除默认值 `STATE_UNSPECIFIED` 外，状态枚举值**不应**使用枚举名称作为前缀。

### 破坏性变更

**简要回答：** 应明确告诉用户状态枚举未来可能增加新值，并谨慎地向现有枚举添加状态。

虽然向现有状态枚举增加状态*可能*破坏用户代码，但增加状态不被视为破坏性变更。考虑只有 `ACTIVE` 和 `DELETED` 两个值的状态。用户可能编写代码检查 `if state == ACTIVE`，然后简单地在其他分支假定资源已删除。如果 API 后来为另一种用途增加新状态，这段代码就会出错。

我们最终无法控制用户的这种行为，但 API 文档**应**积极鼓励用户编写代码时预期状态枚举未来可能收到新值。

API **可以**在适当时向现有 State 枚举增加新状态，增加新状态*不*被视为破坏性变更。

### 何时避免使用状态

有时，`State` 枚举并不是 API 的最佳选择，尤其是在潜在状态很少，或状态不是互斥的情况下。

仍以只有 `ACTIVE` 和 `DELETED` 的状态为例。在这种情况下，API 可能更适合暴露 `google.protobuf.Timestamp delete_time`，并让用户根据该字段是否设置来判断资源是否被删除。

### 常见状态

以下列出常见状态。确定状态名称时，API **应**参考既有实践；如果先例冲突，**应**优先考虑本地一致性，而不是全局一致性。

#### 静止状态

“静止状态”是指在没有用户操作时预期会无限期保持的生命周期状态。不过，用户可以发起操作，将处于静止状态的资源转移到某些其他状态（静止或活动）。

- `ACCEPTED`
- `ACTIVE`
- `CANCELLED`
- `DELETED`
- `FAILED`
- `SUCCEEDED`
- `SUSPENDED`
- `VERIFIED`

#### 活动状态

“活动状态”是指通常会自行解析为某个预期静止状态的生命周期状态。

**注意：** 只暴露对客户有用的状态。只有资源会在活动状态中停留足够长时间时，活动状态才有价值。如果状态变化立即完成，就不需要活动状态。

- `CREATING`（通常变为 `ACTIVE`）
- `DELETING`（通常变为 `DELETED`）
- `PENDING`（通常变为 `RUNNING`）
- `REPAIRING`（通常变为 `ACTIVE`）
- `RUNNING`（通常变为 `SUCCEEDED`）
- `SUSPENDING`（通常变为 `SUSPENDED`）
