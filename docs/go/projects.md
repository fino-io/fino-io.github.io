# 12.3. 综合实验、数据集与交付

先修建议：[实战：日志统计 CLI](./project-cli)、[实战：任务管理 API](./project-api)。

## 用阶段产物判断学习进展 {#concept-1}

读完章节只是输入，能够解释、修改和测试一个操作才形成输出。综合项目按阶段验收，每个阶段只扩展必要的一项能力。

| 阶段 | 可交付产物 | 你需要能解释 |
| --- | --- | --- |
| 顺序程序 | 文件处理 CLI | 数据类型、错误和输入边界。 |
| 并发程序 | 有界任务流水线 | 任务结束、队列上限、关闭和取消。 |
| 网络服务 | 有测试的任务 API | 请求契约、共享状态、失败与关闭。 |
| 持久化扩展 | 数据库、迁移和集成测试 | 约束、事务、重启语义与权限。 |
| 诊断扩展 | 原始测量与复测报告 | 证据、瓶颈、变化和平台条件。 |

已经通过的行为测试继续保留，新的需求新增相应断言；不要把大规模目录搬迁、依赖升级和业务改动混成一个不可解释的步骤。

## 职责清楚，比层数多更重要 {#concept-2}

小 CLI 保留一个 main 包，解析逻辑接受 Reader、输出接受 Writer；小 API 先让 HTTP 校验、状态操作与入口装配可独立阅读。出现持久化、多个入口或复杂业务时再拆包，不因架构名称而引入空洞层级。

| 职责 | 负责 | 避免 |
| --- | --- | --- |
| 入口 | 配置、依赖装配、启动、停止 | 埋入业务判断。 |
| HTTP / CLI 边界 | 外部输入校验、状态与退出码映射 | 直接操纵数据库事务细节。 |
| 业务操作 | 业务规则、工作流、错误语义 | 依赖具体 HTTP 请求类型。 |
| 存储实现 | 查询、事务、数据约束映射 | 决定 HTTP 状态码。 |
| 外部客户端 | 认证、协议、超时、响应校验 | 进行无限重试或泄露凭据。 |

业务操作需要存储时，在使用方定义只包含必需操作的接口；不要把 CRUD 全部生成进“通用 Repository”。读取与写入的事务边界来自业务一致性需求，不能通过一套万能抽象隐藏。

## 迭代计划 {#concept-3}

1. **写契约**：定义输入、成功输出、失败情况、规模限制与数据生命周期。
2. **最小纵向流程**：读输入、执行一次操作、输出结果，确保端到端可运行。
3. **增加回归测试**：覆盖空输入、非法数据、依赖失败和边界值。
4. **并发与资源检查**：明确锁、取消、连接释放与退出条件。
5. **复用生态方案**：出现复杂 CLI、数据库、认证需求再引入成熟工具。
6. **验证交付**：从干净目录照 README 运行，复现测试与错误场景。

每一步都能演示实际行为。重构前固定行为，重构后跑同一套测试；不要把目录搬迁、依赖升级与业务改动一次混在一起。

## 两个项目的检查单 {#concept-4}

| 项目 | 必须能解释 | 下一步扩展 |
| --- | --- | --- |
| 日志 CLI | 空输入、行号、大小上限、固定输出、退出码 | 结构化输出、日期分组、更多子命令。 |
| 任务 API | CRUD、分页、body 限制、锁、状态码、关闭 | 数据库、认证、版本冲突、指标。 |

两份项目源码都可在对应章节复制运行，不需要先安装框架。扩展时保留已有测试，新增需求新增必要的行为验证。数据库版本与生产环境的测试数据要隔离，不通过清空真实数据来验证迁移。

## README 应包含什么 {#concept-5}

- 项目用途、明确限制和适用数据规模。
- Go 与外部服务要求，依赖与工具的确定版本。
- 从初始化到构建运行的命令，最小输入与预期输出。
- 配置来源、样例配置、退出码或 HTTP 错误约定。
- 测试、race、vet 与漏洞检查的执行方式。
- 数据存储、备份或重启语义，以及停止方式。

CI 复用团队已有模板，最小流程是格式检查、测试、vet 与构建；按应用风险增加 race、集成测试和 govulncheck。一次验证通过后，有新改动或失败线索再扩大检查范围，不为了仪式感重复跑所有工具。

## 贯穿路线的综合实验 {#concept-6}

| 阶段 | 合成数据与任务 | 必须提交的验证结果 |
| --- | --- | --- |
| 基础 | 词频、权限位、中文文本、集合交集 | 空输入、非法值、共享修改与稳定排序断言。 |
| 类型与错误 | 内存存储 + Reader/Sender 替身 | 动态 nil、包装识别、失败传播、公开接口编译断言。 |
| 并发 | 固定 worker 的平方流水线 | 活动任务上限、取消完成通知、总和、race。 |
| 标准库 | 配置、嵌入资源与日志输入 | 严格字段、大小限制、EOF 与输出形状。 |
| 服务 | 任务 CRUD 与数据库升级 | 状态码、分页、事务回滚、用户归属、关闭。 |
| 进阶 | Benchmark、heap、生成与插件 | 原始测量数据、生成一致、平台与工具链条件。 |

每个实验用可复现输入，不依赖真实用户数据或第三方网站稳定性。学习数据入口：

- <a href="/go/data/logs-valid.jsonl" download>有效日志</a>：INFO 2、WARN 1、ERROR 1，含一行空行。
- <a href="/go/data/logs-invalid.jsonl" download>错误日志</a>：第 3 行 DEBUG，应失败且不输出成功统计。
- [任务请求用例](/go/data/task-requests.json)：描述创建、完整替换、非法字段与未知任务的预期状态。
- [Benchmark 规模](/go/data/benchmark-sizes.json)：统一输入规模、重复次数与比较字段。

数据是实验 fixture，不是生产样本；文档与样本一起维护，验收测试读取同一契约。

## 从两个项目推进到三个里程碑 {#concept-7}

**里程碑一**：日志 CLI 能从文件/标准输入处理完整数据，异常输入返回行号，stdout/stderr 与退出码正确。

**里程碑二**：任务 API 内存版本通过所有契约与并发测试，明确重启清空；HTTP 层和核心逻辑可分别测试。

**里程碑三**：为 API 接入 PostgreSQL、迁移、用户归属授权、版本冲突与结构化日志，用集成测试验证真实约束。此阶段新增需求，不把教学内存版包装成生产方案。

每次扩展只引入现实需要的库。Cobra 管命令、pgx 管数据库访问、errgroup 管相关任务、protoc 生成 RPC，不把业务规则隐藏在通用平台里。

## 练习与验收 {#lab}

1. 让一位没有看过代码的人按 README 运行一个项目，记录缺失说明。
2. 将任务 API 存储换成数据库，指出接口、业务与存储中各需要改哪些内容。
3. 写一页架构说明，只解释职责、数据流与生命周期，不罗列设计模式。

验收：项目能从干净环境复现，架构能用具体操作解释，每个新增抽象都有现实用途。目录建议参考 [官方模块组织](https://go.dev/doc/modules/layout)。
