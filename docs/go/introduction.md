# 1.1. Go 的定位、历史与运行模型

Go 学习先回答三个问题：源码怎样变成进程、数据怎样在函数间传递、并发工作由谁结束。本章建立后续章节共同使用的运行模型。

## Go 为什么出现，适合什么工作

Go 在 2009 年公开，围绕大型软件团队的构建效率、可读性与并发需求设计。它把静态类型、垃圾回收、快速编译、轻量并发与统一工具链放在一起。历史与设计背景参见 [官方 FAQ](https://go.dev/doc/faq)。

选择语言时看约束：团队需要易读接口、网络 I/O 并发、CLI 或基础设施程序时，Go 很合适；严格无 GC 延迟、浏览器界面或领域已有强工具链时，需要继续比较方案。GC 简化释放对象的工作，但文件、连接、goroutine 都仍须显式管理。简单语法不意味着简单的并发和故障处理。

## 从源码到进程

```text
.go 源文件 → 包检查与编译 → 链接 → 可执行文件 → 操作系统进程
                   ↑                         ↓
             go.mod 依赖与版本         Go runtime：调度、GC、栈
```

一个目录的文件组成包；编译器按导入依赖构建包，链接器连接入口与依赖。`go run` 临时完成编译、链接和运行，`go build` 生成供以后启动的文件。可执行文件包含 Go runtime，不能因此推断“没有系统依赖”：cgo、证书、文件、网络和部署平台仍可能是运行条件。

## 实验：构建产物不是源码的实时视图

保存为 main.go：

```go
package main

import "fmt"

func main() { fmt.Println("版本 A") }
```

```sh
go mod init example.com/first
go build -o first .
./first
```

输出版本 A。把源码改成版本 B 后再次执行 `./first`，仍输出 A；重新 build 才得到 B，`go run .` 则编译当前源码后输出 B。这个实验说明为什么部署后改文件、修改本地配置却不重建静态文档时，运行结果可能没有变化。

## 语言约束怎样帮助协作

Go 用统一格式代替团队争论；导出名字按首字母大写识别；未使用的局部变量和导入会直接报错；异常返回显式出现在签名中。接口由方法集隐式实现，不要求建立继承树。更少的语法分支把复杂度留给数据、边界和生命周期，学习时要把注意力放在那里。

不是所有官方历史材料都覆盖现代语言：旧代码可能使用 GOPATH 布局、ioutil 或过时的循环变量规则。阅读成熟课程时理解概念，再以当前官方文档核对 API。本站示例最低要求 Go 1.22，实际学习建议受支持稳定版本；高级与第三方示例注明额外条件。

## 学习实验与判定 {#lab}

1. 构建 A，修改源码为 B，不重新构建再运行。正确结果应仍为 A。
2. 写下程序需要的外部条件：端口、数据文件、环境变量和数据库分别属于哪一类？
3. 给一个网络巡检工具与一个硬实时控制器做语言选型，列出约束而非罗列宣传优点。

通过标准：能画出构建与运行的数据流，明确 GC 管理对象内存而不管理所有资源。下一章完成实际环境与命令实验。
