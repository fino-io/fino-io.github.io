# 19 · 从练习到完整项目

本章目标：把“示例能运行”推进到“别人按说明也能使用”。前面的三个实战项目已经提供完整实现，本章说明如何选项目、独立扩展并完成交付。先选一个与你的实际需求有关的小问题，完成一次输入、处理、输出和验证的闭环。

## 按能力选择起点

| 当前能力 | 推荐项目 | 第一版完成标准 |
| --- | --- | --- |
| 会写函数、读文件、处理异常 | [CSV 消费报告 CLI](./project-cli) | 给定样本生成正确报告，无效行给出原因，失败返回非零退出码。 |
| 理解 HTTP、SQL 和类型校验 | [任务管理 API](./project-api) | 创建、查询、更新可用，重启保留数据，测试使用临时数据库。 |
| 能处理表格并解释统计结果 | [月度消费分析](./project-data) | 重复与缺失有明确规则，聚合金额可核对，重复执行结果一致。 |

已经完成示例的读者，选择一个新需求再实现：CLI 增加月份过滤，API 增加按状态查询，分析项目增加分类占比。一个需求从设计到验收走完后，再增加下一个；不要同时加入用户系统、队列、容器和多种数据库。

## 先写一页需求说明

以“CSV 报告增加月份过滤”为例，动手前写清楚以下约定：

- **使用者与场景**：个人在终端查看某个月的分类支出。
- **输入**：现有 CSV 与可选的 `--month YYYY-MM` 参数。
- **输出**：仍以整数分输出 JSON；没有匹配记录时返回 `{}`。
- **失败**：月份格式错误、CSV 损坏、读写失败都返回非零退出码。
- **范围**：不增加退款、币种转换或在线账户同步。
- **验收**：一月与二月分别匹配；不传月份时行为与原版一致。

进一步明确一个容易遗漏的规则：筛选月份时，是否仍校验其他月份的无效记录？本指南建议先校验整份输入再筛选，保证报告不会默默略过坏数据。也可以选择另一种行为，但必须在说明与测试中保持一致。

## 用职责划分代码

第一版保留单文件通常足够。CLI 参数、数据解析和汇总逻辑开始互相干扰时，再沿实际职责拆分：

```text
expense-report/
├── pyproject.toml
├── README.md
├── examples/
│   └── expenses.csv
├── src/
│   └── expense_report/
│       ├── __init__.py
│       ├── cli.py
│       └── report.py
└── tests/
    ├── test_report.py
    └── test_cli.py
```

`report.py` 负责校验和聚合，`cli.py` 负责参数、文件路径和输出。计算函数不直接终止进程，入口将可预期的异常转换为用户消息与退出码。API 项目同样区分输入模型、业务规则与数据库操作；只有复杂度增加时才拆模块，不预设多层架构。

复用标准库和成熟生态：参数解析先用 argparse，HTTP 用 HTTPX，测试用 pytest，Web 用 FastAPI 或 Django，数据分析用 pandas。先确认现有工具是否满足需求，再考虑自行实现。

## 按里程碑推进

| 阶段 | 需要交付 | 如何验证 |
| --- | --- | --- |
| 1 · 跑通最小流程 | 一份合成输入和一个正常结果 | 手工核对每条记录与总数。 |
| 2 · 明确失败边界 | 参数、字段、编码和数值校验 | 故意构造错误输入，确认原因与定位信息。 |
| 3 · 组织工程 | 模块、依赖声明、命令入口 | 从新环境按 README 安装和运行。 |
| 4 · 保留回归检查 | 业务测试和少量入口测试 | 修改规则后，原有行为仍通过。 |
| 5 · 交付与复盘 | 使用说明、已知限制和样例 | 请未参与开发的人照说明完成一次操作。 |

每个阶段都应能独立演示。遇到不确定的库 API，先用最小脚本验证，再接入业务；不要在主流程里同时试验多种方案。

## 测试哪些行为

纯逻辑测试覆盖金额解析、边界日期、筛选和排序；文件测试覆盖中文、带引号字段、缺列与空输入。CLI 至少验证成功退出码、失败退出码和帮助文本；API 测试覆盖校验、缺失记录、分页与持久化；分析测试核对记录数、金额总和与输出稳定性。

测试不能依赖个人文件、真实账户或当前互联网状态。使用 tmp_path、合成数据和受控的模拟响应。网络、时间或随机数影响结果时，明确提供可替换的输入。测试公开行为，避免与每个内部函数一一对应。

验证顺序是：针对新需求运行相关测试 → 运行项目完整测试 → 检查格式和类型 → 在干净环境演示安装与启动。已有检查通过后，不必反复扩大验证范围。

## 交付检查清单

- README 说明 Python 版本、安装、启动、输入格式、输出单位和常见失败。
- 依赖可以重建，虚拟环境和缓存不作为交付内容；应用按所选工具保存锁文件。
- 样本是合成或已脱敏数据，配置与凭据通过明确的外部入口提供。
- 写文件说明覆盖行为；服务说明存储路径、备份方式和部署边界。
- 项目有可复制的验证命令，已知限制写清楚，错误不会伪装成成功。

交付不一定意味着发布到包仓库或部署到公网。本地工具先让另一台机器能按说明运行；需要分享安装包时，再按 [Python 打包指南](https://packaging.python.org/en/latest/tutorials/packaging-projects/) 构建和检查 wheel。

## 练习与验收

1. 为三个项目中的一个写一页新需求说明，包含正常、边界和失败场景。
2. 在不查看最终实现的情况下完成扩展，再对照已有测试检查兼容性。
3. 删除临时环境后重新安装，按 README 运行样本并核对输出。
4. 记录一个实际踩过的问题和解决步骤，加入项目说明。

验收：能解释项目的数据流、职责边界与失败策略，别人可以复现你的结果。完成后进入 [20 · 资料、方向与常见问题](./resources)，选择下一条学习主线。
