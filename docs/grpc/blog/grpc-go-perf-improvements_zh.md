在过去的几个月里，我们一直致力于提高 gRPC-Go 的性能。这包括提高网络利用率、优化 CPU 使用率和内存分配。我们最近的大部分工作都集中在改进 gRPC-Go 流控制上。经过多次优化和新功能后，我们已经能够显着改进，特别是在高延迟网络上。我们希望使用高延迟网络和大消息的用户能够看到一个数量级的性能提升。最后给出基准结果。

本博客总结了我们迄今为止为提高性能所做的工作（按时间顺序），并列出了我们的近期计划。

## 最近实施的优化

### 接收大消息时扩展流窗口

[代码链接](https://github.com/grpc/grpc-go/pull/1248)

这是 gRPC-C 用于实现大消息性能优势的优化。这个想法是，当接收端的应用程序主动读取时，我们可以有效地绕过流级流量控制来请求整个消息。事实证明，这对于处理大消息非常有帮助。由于应用程序已经致力于读取并为其分配了足够的内存，因此我们发送主动大窗口更新（如果有必要）来获取整个消息是有意义的，而不是分块接收消息并在窗口不足时发送窗口更新。

仅此优化就为高延迟网络上的大消息提供了 10 倍的改进。


### 将应用程序读取与连接流控制解耦

[代码链接](https://github.com/grpc/grpc-go/pull/1265)

在与 gRPC-Java 和 gRPC-C 核心团队进行多次讨论后，我们意识到 gRPC-Go 的连接级流量控制过于严格，因为连接上的窗口更新取决于应用程序是否从中读取数据。必须注意的是，流级流量控制依赖于应用程序读取是非常有意义的，但对于连接级流量控制来说则不然。基本原理如下：一个连接由多个流（RPC）共享。如果至少有一个流读取缓慢或根本不读取，则会影响性能或完全阻止该连接上的其他流。发生这种情况是因为我们不会在连接上发送窗口更新，直到缓慢或不活动的流读取数据。因此，将连接的流量控制与应用程序读取分离是有意义的。

然而，这至少引发了两个问题：

1. 当数据流用完时，客户端是否能够通过创建新流来向服务端发送尽可能多的数据？

2. 如果流级流控就足够了，为什么还要进行连接级流控？

第一个问题的答案简短而简单：不。服务端可以选择限制它打算同时服务的流的数量。因此，虽然乍一看这似乎是一个问题，但实际上并不是。

连接级流量控制的需要：

确实，流级流量控制足以阻止发送者发送过多的数据。但是，如果没有连接级流量控制（或使用无限的连接级窗口），那么当流上的速度变慢时，打开一个新的流控制似乎会使速度更快。由于流的数量有限，因此到目前为止只需要一个。然而，将连接级流量控制窗口设置为网络的带宽延迟乘积 (BDP) 会为网络实际可挤出的性能设置上限。


### 搭载窗口更新

[代码链接](https://github.com/grpc/grpc-go/pull/1273)

发送窗口更新本身会产生相关成本；刷新操作是必要的，这会导致系统调用。系统调用是阻塞且缓慢的。因此，当发送流级窗口更新时，检查是否可以使用相同的刷新系统调用发送连接级窗口更新是有意义的。

### BDP估计和动态流量控制窗口

[代码链接](https://github.com/grpc/grpc-go/pull/1310)

此功能是最新的，在某些方面也是最受期待的优化功能，它帮助我们缩小了高延迟网络上 gRPC 和 HTTP/1.1 性能之间的最终差距。

带宽延迟乘积 (BDP) 是网络连接的带宽与其往返延迟的乘积。  这有效地告诉我们，如果实现充分利用，在给定时刻可以“在线”有多少字节。

计算 BDP 并进行相应调整的[算法](https://docs.google.com/document/d/1Eq4eBEbNt1rc8EYuwqsduQd1ZfcBOCYt9HVSBa--m-E/pub) 首先由 @ejona 提出，后来由 gRPC-C 核心和 gRPC-Java 实现（请注意，Java 中尚未启用该算法）。这个想法简单而强大：每次接收器收到数据帧时，它都会发出 BDP ping（带有仅由 BDP 估计器使用的唯一数据的 ping）。此后，接收方开始计算其接收到的字节数（包括触发 BDP ping 的字节数），直到收到该 ping 的 ack。在大约 1.5 RTT（往返时间）内接收到的所有字节的总和是有效 BDP * 1.5 的近似值。如果这接近我们当前的窗口大小（例如，超过 2/3），我们必须增加窗口大小。我们将窗口大小（流和连接）设置为我们采样的 BDP（接收到的所有字节的总和）的两倍。

该算法本身可能会导致 BDP 估计无限增加；窗口的增加将导致采样更多字节，进而导致窗口进一步增加。这种现象称为“缓冲区膨胀”(https://en.wikipedia.org/wiki/Bufferbloat)，是由 gRPC-C 核心和 gRPC-Java 的早期实现发现的。解决方案是计算每个样本的带宽并检查它是否大于迄今为止记录的最大带宽。如果是这样，只有增加我们的窗口大小。我们知道，带宽可以通过将样本除以 RTT * 1.5 来计算（请记住样本是一次半往返）。如果带宽没有随着采样字节的增加而增加，则表明这种变化是由于窗口大小增加而导致的，并且并不能真正反映网络本身的性质。

在不同大陆的虚拟机上运行实验时，我们意识到，每隔一段时间，在正确的时间（实际上是错误的时间）出现的恶意的、不自然的快速 ping-ack 会导致我们的窗口大小增大。发生这种情况是因为这样的 ping-ack 会导致我们注意到 RTT 降低并计算出较高的带宽值。现在，如果该字节样本大于窗口的 2/3，那么我们将增加窗口大小。然而，这个 ping ack 是一种异常现象，不应该改变我们对网络 RTT 的看法。因此，我们保留我们记录的 RTT 的运行平均值，并按常数而不是样本总数进行加权，以更多地关注最近的 RTT，而不是过去的 RTT。这很重要，因为网络可能会随着时间而改变。

在实现过程中，我们尝试了几个调整参数，例如根据样本大小计算窗口大小的乘数，以选择最佳设置，在增长和准确性之间取得平衡。

鉴于我们始终受到 TCP 流量控制的约束（在大多数情况下上限为 4MB），我们将窗口大小的增长限制为相同的数字：4MB。

默认情况下，BDP 估计和动态调整窗口大小处于打开状态，可以通过手动设置连接和/或流窗口大小的值来关闭。

### 近期的努力

我们现在正在研究通过提高 CPU 利用率来提高吞吐量，以下工作与此一致。

### 减少刷新系统调用

我们注意到传输层中的一个错误，导致我们为写入的每个数据帧进行刷新系统调用，即使同一个 goroutine 有更多数据要发送。我们可以对大量这样的写入进行批处理，以便仅使用一次刷新。事实上这对代码本身来说不会有太大的改变。

为了消除不必要的刷新，我们最近将一元和服务端流 RPC 的标头和数据写入合并为客户端的一次刷新。链接到[代码](https://en.wikipedia.org/wiki/Bufferbloat)

我们的一位用户 @petermattic 在 [this](https://github.com/grpc/grpc-go/pull/1343) PR 中提出的另一个相关想法是将服务端对一元 RPC 的响应合并到一次刷新中。我们目前也在调查此事。

### 减少内存分配

对于从线路读取的每个数据帧，都会发生新的内存分配。对于每一条需要解压缩和解码的新消息，gRPC 层也是如此。这些分配会导致过多的垃圾收集周期，这是昂贵的。重用内存缓冲区可以减少 GC 压力，我们正在为此设计方法原型。由于请求需要不同大小的缓冲区，一种方法是维护固定大小（2 的幂）的单独内存池。因此，现在当从线路读取 x 字节时，我们可以找到最接近的大于 x 的 2 的幂，并重用缓存中的缓冲区（如果可用），或者在需要时分配一个新缓冲区。我们将使用 golang 同步池，因此我们不必担心垃圾收集。然而，在承诺这一点之前，我们需要运行足够的测试。
