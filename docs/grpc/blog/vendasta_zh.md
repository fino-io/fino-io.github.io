Vendasta 成立于 8 年前，是一家为小型企业提供单点解决方案的产品提供商。从一开始，我们就与拥有大量销售人员并与这些企业建立现有关系的媒体公司和机构合作来销售我们的软件。据估计，仅美国就有超过 3000 万家小型企业，因此我们的 SaaS 解决方案的可扩展性从一开始就被视为我们最关心的问题之一，这也是我们开始使用 [Google App Engine](https://cloud.google.com/appengine/) 和数据存储区的原因。当我们的系统从数百个最终用户扩展到数十万个时，该解决方案对我们来说非常有效。我们还将我们的产品从单点解决方案扩展到包含多种产品的整个平台，以及合作伙伴在此期间管理这些产品销售的工具。

在整个旅程中，Python GAE 很好地满足了我们的需求。我们通过 HTTP + JSON 公开了许多 API，供我们的合作伙伴自动执行任务并将他们的其他系统与我们的产品和平台集成。然而，我们在 2016 年推出了 Vendasta 市场。这标志着我们的产品发生了重大变化，我们的产品在很大程度上依赖于第三方供应商使用我们的 API 在我们的平台上交付他们自己的产品。这是一个重大变化，因为我们的公共 API 为第 3 方应用程序提供了上限，并让我们意识到我们确实需要制作令人惊叹的 API，而不仅仅是好的 API。

我们开始的第一个优化是使用 Go 编程语言来构建端点，与使用 Python 相比，该端点能够以更低的延迟处理更高的吞吐量。在某些 API 上，这产生了令人难以置信的差异：我们看到第 50 个百分点的响应时间从 1200 毫秒下降到 4 毫秒，更引人注目的是第 99 个百分点的响应时间从 30,000 毫秒下降到 12 毫秒！在其他 API 上，我们看到了一个小得多的差异，但仍然很显着。

我们使用的第二个优化是将大部分数据存储数据复制到 ElasticSearch 中。 ElasticSearch 是一种与 Datastore 根本不同的存储技术，并且不是托管服务，因此这对我们来说是一个巨大的飞跃。但这一变化使我们能够将几乎所有夜间批处理 API 迁移到实时 API。   我们尝试过 BigQuery，但它的查询处理时间意味着我们无法实时显示内容。  我们尝试过cloudSQL，但数据太多，无法轻松扩展。  我们尝试过 appengine 搜索 API，但它在结果集超过 10,000 个时存在局限性。  相反，我们使用 [Google 容器引擎](https://cloud.google.com/container-engine/) 扩展了 ElasticSearch 集群，凭借其强大的聚合和方面处理功能，我们的需求很容易得到满足。  因此，通过前两个解决方案，我们对 API 的性能进行了有意义的更改。

我们所做的最后一个优化是将 API 移至 [gRPC](https://grpc.io/)。这一变化比其他变化更广泛，因为它影响了我们的客户。与 ElasticSearch 一样，它代表了一个具有不同性能特征的根本不同的模型，但与 ElasticSearch 不同的是，我们发现它是一个真正的超集：我们所有的使用场景都受到它的积极影响。


我们从 gRPC 中看到的第一个好处是能够从发布 API 并要求开发人员与其集成，转变为发布 SDK 并要求开发人员复制粘贴用他们的语言编写的示例代码。这对于希望与我们的产品集成的人们来说是一个非常大的好处，同时不需要我们以我们的合作伙伴和供应商使用的 5 种以上语言手动发布整个 SDK。值得注意的是，我们仍然在生成的 gRPC SDK 上编写轻量级包装器，以使它们对包管理器友好，并在生成的 protobuf 结构上提供包装器。

我们从 gRPC 中看到的第二个好处是能够摆脱 HTTP + JSON 所需的调用和响应架构。 gRPC 构建在 HTTP/2 之上，允许客户端和/或服务端流式传输。在我们的用例中，这意味着我们可以在服务端上准备好结果时通过流式传输结果来缩短首次显示的时间（服务端流式传输）。  我们还一直在研究提供非常灵活的创建端点的潜力，这些端点可以轻松支持双向流式传输的批量摄取，这意味着我们将允许客户端异步流式传输结果，而服务端将流回状态，从而允许轻松的检查点操作，同时不会减慢上传速度以等待确认。我们觉得我们才刚刚开始看到此功能的好处，因为它为客户端-服务端交互开辟了一种全新的模型，而这是 HTTP 无法实现的。

第三个好处是从 JSON 到协议缓冲区的切换，这与 gRPC 配合得很好。这提高了序列化和反序列化时间；这对于我们的一些 API 来说非常重要，但对所有 API 都表示赞赏。更重要的好处来自 proto 的显式格式规范，这意味着客户端接收类型化对象而不是自由格式的 JSON。因此，我们的客户可以受益于 IDE 中的自动完成、类型安全（如果他们的语言支持）以及不同版本的客户端和服务端之间的强制兼容性。

gRPC 的最后一个好处是我们能够快速指定端点。数据和服务定义的原型格式极大地简化了新端点的定义，并最终允许端点契约的简洁定义。  这意味着我们能够更好地在开发团队之间沟通端点规范。  gRPC 意味着我们公司第一次能够同时开发 API 的客户端和服务端！  这意味着我们使用随附的 SDK 生成新 API 的延迟已大幅下降。  与代码生成相结合，它使我们能够真正并行开发客户端和服务端。

我们在 gRPC 方面的经验是积极的，尽管它并没有消除向合作伙伴和供应商提供端点的困难，也没有解决我们所有的性能问题。然而，它确实改进了我们的端点性能、与这些端点的集成，甚至是 SDK 的交付。
