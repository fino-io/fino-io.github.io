## 动机

十多年来，Google 一直使用名为 Stubby 的单一通用 RPC 基础设施来连接数据中心内部和数据中心之间运行的大量微服务。我们的内部系统长期以来一直采用当今流行的微服务架构。拥有统一的跨平台 RPC 基础设施可以在整个车队范围内提高效率、安全性、可靠性和行为分析，这对于支持这一时期令人难以置信的增长至关重要。

Stubby 具有许多出色的功能 - 然而，它不基于任何标准，并且与我们的内部基础设施耦合过于紧密，不适合公开发布。随着 SPDY、HTTP/2 和 QUIC 的出现，许多相同的功能以及 Stubby 不提供的其他功能已经出现在公共标准中。很明显，是时候重新设计 Stubby 以利用这种标准化，并将其适用性扩展到移动、物联网和云用例。

## 原则和要求

### 服务不是对象，消息不是引用

推广系统间粗粒度消息交换的微服务设计理念，同时避免[分布式对象的陷阱](https://martinfowler.com/articles/distributed-objects-microservices.html)和[忽略网络的谬误](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing)。

### 覆盖范围和简单性

该堆栈应该可在每个流行的开发平台上使用，并且可以轻松地为他们选择的平台构建。它应该在 CPU 和内存有限的设备上可行。

### 免费开放

使基本功能免费供所有人使用。将所有工件作为开源项目发布，并授予许可，以促进而不是阻碍采用。

### 互操作性和范围

有线协议必须能够经受住通用互联网基础设施的遍历。

### 通用和高性能

该堆栈应该适用于广泛的用例，同时与特定于用例的堆栈相比，性能几乎没有牺牲。

### 分层

堆栈的关键方面必须能够独立发展。对有线格式的修改不应破坏应用层绑定。

### 负载不可知

不同的服务需要使用不同的消息类型和编码，例如protocol buffers、JSON、XML和Thrift；协议和实现必须考虑到这一点。同样，有效负载压缩的需求因用例和有效负载类型而异：协议应允许可插入的压缩机制。

### 流媒体

存储系统依靠流和流控制来表达大型数据集。其他服务（例如语音转文本或股票行情）依靠流来表示时间相关的消息序列。

### 阻塞和非阻塞

支持客户端和服务端交换的消息序列的异步和同步处理。这对于某些平台上的扩展和处理流至关重要。

### 取消和超时

操作可能成本高昂且寿命较长——取消允许服务端在客户端表现良好时回收资源。当跟踪工作的因果链时，取消可能会级联。客户端可以指示调用超时，这允许服务根据客户端的需求调整其行为。

### 跛鸭

必须允许服务端通过拒绝新请求同时继续处理正在进行的请求来正常关闭。

### 流量控制

客户端和服务端之间的计算能力和网络容量往往不平衡。流量控制可以实现更好的缓冲区管理，并提供针对过度活跃对等点的 DOS 保护。

### 可插拔

有线协议只是功能 API 基础设施的一部分。大型分布式系统需要安全、健康检查、负载均衡和故障转移、监控、跟踪、日志记录等。实现应该提供扩展点以允许插入这些功能，并且在有用的情况下提供默认实现。

### 作为 API 的扩展

需要服务之间协作的扩展应尽可能使用 API 而不是协议扩展。这种类型的扩展可以包括健康检查、服务自省、负载监控和负载均衡分配。

### 元数据交换

认证或跟踪等常见的横切问题依赖于不属于服务声明接口一部分的数据交换。部署依赖于它们以与服务公开的各个 API 不同的速率发展这些功能的能力。

### 标准化状态码

客户端通常以有限的方式响应 API 调用返回的错误。应限制状态码命名空间以使这些错误处理决策更加清晰。如果需要更丰富的特定于域的状态，则可以使用元数据交换机制来提供。
