### 一般的

* 尽可能始终**重复使用存根和通道**。

* **使用 keepalive ping** 来保持 HTTP/2 连接在以下时间段内保持活动状态：
不活动以允许快速无延迟地进行初始 RPC（即 C++ 通道参数 GRPC_ARG_KEEPALIVE_TIME_MS）。

* **处理时使用流式 RPC**
从客户端到服务端、服务端到客户端或双向的长期逻辑数据流。 Streams 可以避免连续的 RPC 启动，包括客户端的连接负载均衡、在传输层启动新的 HTTP/2 请求以及在服务端调用用户定义的方法处理程序。

然而，流一旦启动就无法进行负载均衡，并且很难调试流故障。它们还可能会小规模地提高性能，但会因负载均衡和复杂性而降低可扩展性，因此仅当它们为应用程序逻辑提供显着的性能或简单性优势时才应使用它们。使用流来优化应用程序，而不是 gRPC。

***旁注：*** *这不适用于 Python（有关详细信息，请参阅 Python 部分）。*

* *（专题）* 每个 gRPC 通道使用 0 个或多个 HTTP/2 连接，并且每个连接
通常对并发流的数量有限制。当连接上的活动 RPC 数量达到此限制时，其他 RPC 将在客户端中排队，并且必须等待活动 RPC 完成才能发送。     由于这种排队，具有高负载或长期流式 RPC 的应用程序可能会遇到性能问题。有两种可能的解决方案：

1. **为每个高负载区域创建一个单独的通道**
应用。

2. **使用 gRPC 通道池**来分发 RPC
多个连接（通道必须具有不同的通道参数以防止重复使用，因此定义特定于使用的通道参数，例如通道号）。

***旁注：*** *gRPC 团队计划添加一项功能来修复这些性能问题（请参阅 [grpc/grpc#21386](https://github.com/grpc/grpc/issues/21386) 了解更多信息），因此任何涉及创建多个通道的解决方案都是临时解决方案，最终不需要。*

### C++

* **不要对性能敏感的服务端使用 Sync API。** 如果性能
和/或资源消耗不是问题，请使用 Sync API，因为它对于低 QPS 服务实现起来最简单。

* **对于大多数 RPC，优先使用回调 API，而不是其他 API**，因为
应用程序可以避免所有阻塞操作，或者可以将阻塞操作移至单独的线程。回调 API 比完成队列异步 API 更容易使用，但目前对于真正的高 QPS 工作负载来说速度较慢。

* 如果必须使用异步完成队列 API，**最好的可扩展性
权衡是拥有 `numcpu` 的线程。** 与线程数量相关的理想完成队列数量可能会随着时间的推移而变化（随着 gRPC C++ 的发展），但从 gRPC 1.41（2021 年 9 月）开始，每个完成队列使用 2 个线程似乎可以提供最佳性能。

* 对于异步完成队列 API，请确保**注册足够的服务端
请求所需的并发级别**，以避免服务端持续陷入缓慢的路径，从而导致本质上串行请求处理。

**（专题）*
[gRPC::GenericStub](https://grpc.github.io/grpc/cpp/grpcpp_2generic_2generic__stub_8h.html) 在原型序列化上存在高争用/CPU 时间的某些情况下可能很有用。此类允许应用程序直接发送**原始 gRPC::ByteBuffer 作为数据**，而不是从某些原型进行序列化。如果多次发送相同的数据，并且先进行一次显式的原始到 ByteBuffer 序列化，然后再进行多次 ByteBuffer 发送，那么这也会很有帮助。

### Java

* **使用非阻塞存根**来并行化 RPC。

* **提供一个自定义执行器，根据您的工作负载限制线程数量**（缓存（默认）、固定、forkjoin 等）。

### Python

* 流式 RPC 创建额外的线程来接收和可能发送
消息，这使得 gRPC Python 中的流式 RPC 比一元 RPC 慢得多，这与 gRPC 支持的其他语言不同。

* **使用 [asyncio](https://grpc.github.io/grpc/python/grpc_asyncio.html)** 可以提高性能。

* 在同步堆栈中使用未来的 API 会导致创建额外的
线。 **如果可能的话，避免使用未来的 API**。

* *（实验性）* 实验性 **单线程一元流
实现**可通过 [SingleThreadedUnaryStream 通道选项](https://github.com/grpc/grpc/blob/master/src/python/grpcio/grpc/experimental/__init__.py#L38) 实现，每条消息最多可节省 7% 的延迟。
